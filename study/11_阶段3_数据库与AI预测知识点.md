## 1. SQLAlchemy ORM 核心概念

### 概念

ORM（Object-Relational Mapping，对象关系映射）是指用 Python 类来表示数据库表，用类的属性表示表的列，用类的实例表示表的一行数据。开发者操作 Python 对象，ORM 负责生成 SQL 并执行。

| 传统手写 SQL | SQLAlchemy ORM |
|-------------|---------------|
| `SELECT * FROM users WHERE username='admin'` | `db.query(User).filter(User.username=='admin').first()` |
| `INSERT INTO users (...) VALUES (...)` | `db.add(user_obj)` → `db.commit()` |
| 容易 SQL 注入 | 自动参数化，防注入 |
| 换数据库要改 SQL 语法 | 换连接串即可，ORM 适配方言 |
| 字段拼错运行时才报错 | 字段拼错 IDE 直接标红 |

**核心三件套**：

```
Engine（引擎）
  │  负责连接数据库，管理连接池
  │
  ├── SessionLocal（会话工厂）
  │     每次调用 SessionLocal() 创建一个独立会话
  │     会话 = 一次数据库交互的上下文（事务隔离级别在此）
  │
  └── Base（声明式基类）
        所有 ORM 模型继承它，Base.metadata 记录所有表定义
        Base.metadata.create_all(engine) 一行建全部表
```

**为什么不用 Django ORM？**

| 对比项 | SQLAlchemy | Django ORM |
|--------|-----------|------------|
| 框架耦合 | 独立库，配 FastAPI/Flask 均可 | 绑定 Django |
| SQL 控制 | 可精确控制生成 SQL，支持原生 SQL 回退 | 抽象层较厚 |
| 异步支持 | 1.4+ 原生支持 async | Django 4.x 才支持 |
| 学习曲线 | 较陡，概念多 | 简单直观 |

### 本项目代码（database.py）

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base
from backend.config import settings

# 创建引擎：连接 SQLite 数据库文件
engine = create_engine(settings.DATABASE_URL, connect_args=settings.connect_args)

# 会话工厂：每次调用 SessionLocal() 创建新会话
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# ORM 基类：所有模型继承它
Base = declarative_base()
```

- `autocommit=False`：不自动提交，需要手动 `db.commit()`，保证事务原子性
- `autoflush=False`：不在查询前自动 flush（把 pending 对象写入数据库），避免意外的 SQL 执行
- `bind=engine`：会话通过这个引擎获取数据库连接

### 面试问答

**Q: ORM 和原生 SQL 各有什么优缺点？什么时候用哪个？**
> ORM 优点是开发效率高、防 SQL 注入、跨数据库；缺点是复杂查询生成的 SQL 可能低效、有 N+1 查询问题。简单 CRUD 用 ORM，复杂多表 JOIN、聚合统计、性能关键路径用原生 SQL（SQLAlchemy 支持 `db.execute(text("SELECT ..."))`）。

**Q: `declarative_base()` 做了什么？**
> 创建一个所有 ORM 模型的基类。继承它的子类会被自动注册到 `Base.metadata` 中，调用 `Base.metadata.create_all(engine)` 时遍历所有注册的表定义生成 `CREATE TABLE` SQL。本质是用元类（metaclass）在类定义时收集表结构信息。

**Q: `create_engine` 是立即连接数据库吗？**
> 不是。`create_engine` 是惰性连接——创建引擎对象但不实际连数据库，直到第一次执行 SQL 时才从连接池获取连接。这叫"延迟初始化"，好处是即使数据库暂时不可用，程序也能启动。

## 2. Engine、Session 与依赖注入

### 概念

在 Web 应用中，每个 HTTP 请求需要独立的数据库会话（Session），请求结束后关闭会话。FastAPI 通过依赖注入（Dependency Injection）机制自动管理这一生命周期。

```
HTTP 请求进入
    │
    │  Depends(get_db) 触发
    ↓
get_db() 执行：
    db = SessionLocal()     ← 创建会话
    yield db                ← 把会话交给路由函数（暂停在这里）
    │                         路由函数执行完毕后继续
    ↓
    db.close()              ← 关闭会话（finally 保证执行）
    │
    │  如果路由函数抛异常，finally 也会执行
    ↓
HTTP 响应返回
```

**为什么用 `yield` 而不是 `return`？**
> `yield` 是生成器语法。FastAPI 检测到依赖函数里有 `yield`，会把 `yield` 之后的代码当作"清理逻辑"——无论路由函数成功还是抛异常，清理逻辑（`db.close()`）都会执行。如果用 `return`，路由函数异常时 `db.close()` 不会执行，导致连接泄漏。

### 本项目代码（database.py —— get_db 依赖注入）

```python
def get_db():
    """FastAPI 依赖注入：路由里写 `db: Session = Depends(get_db)` 即可拿到会话。"""
    db = SessionLocal()
    try:
        yield db          # 交给路由函数
    finally:
        db.close()        # 无论成功还是异常，都会关闭
```

**路由中的使用方式（main.py）**：

```python
@app.post("/api/auth/register", response_model=schemas.TokenResponse)
def register(req: schemas.UserRegister, db: Session = Depends(get_db)):
    # ↑ db 参数由 Depends(get_db) 自动注入
    # FastAPI 调用 get_db()，拿到 yield 的 db，传给这个函数
    user = models.User(
        username=req.username,
        email=req.email,
        password_hash=auth.hash_password(req.password),
    )
    db.add(user)          # 添加到会话（还没写入数据库）
    db.commit()           # 提交事务（真正写入）
    db.refresh(user)      # 刷新，获取数据库生成的 id
    return schemas.TokenResponse(...)
```

### 面试问答

**Q: 为什么不全局共享一个 Session？**
> Session 不是线程安全的。FastAPI 用 async/多线程处理并发请求，如果多个请求共用一个 Session，会导致数据互相污染、事务混乱。每个请求独立 Session，隔离互不影响。

**Q: `db.commit()` 和 `db.flush()` 的区别？**
> `flush()` 把会话中的 pending 对象发送到数据库（执行 INSERT/UPDATE SQL），但不提交事务——之后还能 `rollback()` 撤销。`commit()` = `flush()` + `commit transaction`，不可撤销。本项目创建 Fantasy 阵容时用 `db.flush()` 先拿到 `team.id`，再写关联表，最后统一 `commit()`。

**Q: 如果路由函数里 `db.add()` 了但没 `commit()` 会怎样？**
> 请求结束时 `db.close()` 被调用，未提交的事务自动回滚，数据不会写入数据库。所以忘了 `commit()` 不会脏写，但数据丢失了。

## 3. ORM 模型设计（8 张表）

### 概念

本项目的 8 张表覆盖了用户、车手车队、Fantasy 阵容、预测、投票 5 个业务域：

```
┌─────────┐     ┌──────────────┐     ┌──────────────────────┐
│  User   │1───n│ FantasyTeam  │1───n│ FantasyTeamDriver    │
│ 用户表   │     │ 阵容主表     │     │ 阵容-车手关联        │
└─────────┘     └──────────────┘     └──────────────────────┘
                      │1
                      │
                      └──n┐ FantasyTeamConstructor
                      │   │ 阵容-车队关联
                      │   └──────────────────────┐
                      │
┌─────────┐  ┌──────────┐  ┌─────────────┐  ┌─────────┐
│ Driver  │  │Constructor│  │ Prediction  │  │  Vote   │
│ 车手表   │  │ 车队表    │  │ 预测记录    │  │ 投票表   │
└─────────┘  └──────────┘  └─────────────┘  └─────────┘
```

**ER 关系总结**：

| 关系 | 类型 | 说明 |
|------|------|------|
| User → FantasyTeam | 1对多 | 一个用户每站一份阵容 |
| FantasyTeam → FantasyTeamDriver | 1对多 | 一个阵容含多个车手 |
| FantasyTeam → FantasyTeamConstructor | 1对多 | 一个阵容含多个车队 |
| Driver / Constructor | 独立表 | 从 Ergast 同步，不与阵容外键关联 |
| Prediction | 独立表 | 每站每车手一条预测 |
| Vote | 独立表 | 每人每站每类型一条投票 |

### 本项目代码（models.py —— 逐表解析）

**① User 用户表**

```python
class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True, index=True)
    username = Column(String(50), unique=True, nullable=False, index=True)
    email = Column(String(120), unique=True, nullable=False)
    password_hash = Column(String(128), nullable=False)   # bcrypt 哈希
    display_name = Column(String(100))                     # 可空，昵称
    role = Column(String(20), default="user")              # user / admin
    created_at = Column(DateTime, default=datetime.utcnow)

    fantasy_teams = relationship("FantasyTeam", back_populates="user",
                                 cascade="all, delete-orphan")
```

- `unique=True`：用户名和邮箱唯一，注册时检查重复
- `index=True`：在 username 上建索引，加速 `filter(User.username==...)` 查询
- `password_hash` 长度 128：bcrypt 哈希固定 60 字符，128 留余量
- `cascade="all, delete-orphan"`：删除用户时级联删除其 Fantasy 阵容

**② Driver 车手表 & ③ Constructor 车队表**

```python
class Driver(Base):
    __tablename__ = "drivers"

    id = Column(Integer, primary_key=True, index=True)
    driver_ref = Column(String(50), unique=True, nullable=False)  # Ergast driverId
    name = Column(String(100), nullable=False)
    code = Column(String(3))      # 三字母缩写 VER / NOR / LEC
    number = Column(Integer)      # 车号
    nationality = Column(String(50))
    created_at = Column(DateTime, default=datetime.utcnow)
```

- `driver_ref` 是 Ergast 的 `driverId`（如 `max_verstappen`），用于和外部数据源对齐
- `code` 是三字母缩写，Fantasy 阵容用它关联车手（不用外键，因为车手表可能没同步）

**④ FantasyTeam 阵容主表**

```python
class FantasyTeam(Base):
    __tablename__ = "fantasy_teams"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    season = Column(Integer, nullable=False)
    round = Column(Integer, nullable=False)
    chip_used = Column(String(20), default="none")  # none/limitless/wildcard/no_negative
    total_cost = Column(Float, default=0.0)
    total_points = Column(Float, default=0.0)
    is_scored = Column(Boolean, default=False)       # 是否已结算
    created_at = Column(DateTime, default=datetime.utcnow)

    __table_args__ = (
        UniqueConstraint("user_id", "season", "round", name="uq_fantasy_team_user_round"),
    )
```

- `ForeignKey("users.id")`：外键关联 users 表的 id 列
- `is_scored`：比赛结束后管理员结算，置为 True，防止重复结算
- 唯一约束：每人每站只能有一份阵容（详见第 4 节）

**⑤ FantasyTeamDriver & ⑥ FantasyTeamConstructor 关联表**

```python
class FantasyTeamDriver(Base):
    __tablename__ = "fantasy_team_drivers"

    id = Column(Integer, primary_key=True, index=True)
    team_id = Column(Integer, ForeignKey("fantasy_teams.id", ondelete="CASCADE"),
                      nullable=False)
    driver_code = Column(String(10), nullable=False)   # VER / NOR
    is_captain = Column(Boolean, default=False)         # 队长 x2
    price = Column(Float, nullable=False)               # 选取时的价格快照

    team = relationship("FantasyTeam", back_populates="drivers")
    __table_args__ = (
        UniqueConstraint("team_id", "driver_code", name="uq_ftd_team_driver"),
    )
```

- `ondelete="CASCADE"`：删除 FantasyTeam 时自动删除关联车手行
- `price` 存快照：车手价格每站变化，选人时锁定当前价格
- 唯一约束防止同一阵容重复选同一车手

**⑦ Prediction 预测表**

```python
class Prediction(Base):
    __tablename__ = "predictions"

    id = Column(Integer, primary_key=True, index=True)
    season = Column(Integer, nullable=False)
    round = Column(Integer, nullable=False)
    driver_code = Column(String(10), nullable=False)
    probability = Column(Float, nullable=False)   # 0-1 夺冠概率
    rank_pred = Column(Integer, nullable=False)   # 预测排名
    model_version = Column(String(20), default="rule_v1")

    created_at = Column(DateTime, default=datetime.utcnow)
```

- `features_json`：把特征向量序列化成 JSON 存下来，方便复盘和模型迭代对比

**⑧ Vote 投票表**

```python
class Vote(Base):
```

### 面试问答

**Q: 为什么 FantasyTeamDriver 不用外键关联 Driver 表？**
> 因为 Driver 表可能还没同步（需要从 Ergast 拉取），而 Fantasy 阵容提交时前端已经拿到车手列表（直接从 Ergast API 获取）。用 `driver_code`（三字母代码）做软关联，解耦了阵容和车手表的同步状态。代价是无法做 JOIN 查询车手详情，但本项目暂不需要。

**Q: `features_json` 为什么用 Text 而不是 JSON 类型？**
> SQLite 不原生支持 JSON 类型（PostgreSQL 才支持）。用 Text 存 JSON 字符串，读取时 `json.loads()` 解析，跨数据库通用。如果用 PostgreSQL，可以用 `Column(JSON)` 直接查询 JSON 字段。

**Q: `default=datetime.utcnow` 和 `default=datetime.utcnow()` 的区别？**
> `default=datetime.utcnow` 传的是函数引用，每次插入时调用一次，每次得到不同时间。`default=datetime.utcnow()` 传的是函数返回值（一个固定时间），所有行都存同一个时间——这是新手常犯的 bug。

## 4. 唯一约束与联合索引

### 概念

**唯一约束（UniqueConstraint）**：确保某几列的组合值在表中唯一，防止重复数据。

**联合索引（Index）**：在多列上建索引，加速多条件查询。

```sql
-- 唯一约束：每人每站每类型只能投一次
UNIQUE(user_id, season, round, vote_type)

-- 联合索引：加速 WHERE season=2025 AND round=5 AND vote_type='driver_of_day'
INDEX(season, round, vote_type)
```

| 概念 | 作用 | 违反时 |
|------|------|--------|
| 唯一约束 | 防止重复数据 | INSERT 报 IntegrityError |
| 联合索引 | 加速查询 | 无报错，只是慢 |
| 唯一约束 = 隐式索引 | 唯一约束自动创建索引 | — |

### 本项目代码（models.py —— 三处唯一约束）

```python
# 1. FantasyTeam：每人每站只能一份阵容
class FantasyTeam(Base):
    __table_args__ = (
        UniqueConstraint("user_id", "season", "round",
                         name="uq_fantasy_team_user_round"),
    )

# 2. FantasyTeamDriver：同一阵容不能重复选同一车手
class FantasyTeamDriver(Base):
    __table_args__ = (
        UniqueConstraint("team_id", "driver_code",
                         name="uq_ftd_team_driver"),
    )

# 3. Vote：每人每站每类型只能投一次
class Vote(Base):
    __table_args__ = (
        UniqueConstraint("user_id", "season", "round", "vote_type",
                         name="uq_vote_user_round_type"),
        Index("idx_vote_round", "season", "round", "vote_type"),  # 额外联合索引
    )
```

**投票接口的"先查后更新/插入"模式（main.py）**：

```python
@app.post("/api/vote")
def cast_vote(req: schemas.VoteCreate,
              user: models.User = Depends(auth.get_current_user),
              db: Session = Depends(get_db)):
    # 先查是否已投票
    existing = db.query(models.Vote).filter(
        models.Vote.user_id == user.id,
        models.Vote.season == req.season,
        models.Vote.round == req.round,
        models.Vote.vote_type == "driver_of_day"
    ).first()

    if existing:
        # 已投过 → 更新
        existing.driver_code = req.driver_code
        existing.voted_at = datetime.utcnow()
        db.commit()
        return {"message": "投票已更新", "driver_code": req.driver_code}
    else:
        # 没投过 → 新建
        vote = models.Vote(user_id=user.id, season=req.season,
                           round=req.round, driver_code=req.driver_code)
        db.add(vote)
        db.commit()
        return {"message": "投票成功", "driver_code": req.driver_code}
```

### 面试问答

**Q: 有了唯一约束为什么还要"先查后插"？直接 INSERT 让数据库报错不行吗？**
> 可以，但让数据库报 `IntegrityError` 后再处理，代码不够优雅。先查后插可以返回友好的错误提示（"已投过票"），而不是 500 错误。而且更新投票需要拿到已有记录修改 `driver_code`，直接 INSERT 做不到更新。生产环境可以用 `INSERT ... ON CONFLICT UPDATE`（PostgreSQL 的 upsert 语法）一步到位。

**Q: 联合索引的列顺序有什么讲究？**
> 遵循"最左前缀原则"。`INDEX(season, round, vote_type)` 能加速 `WHERE season=?`、`WHERE season=? AND round=?`、`WHERE season=? AND round=? AND vote_type=?`，但不能加速 `WHERE round=?`（跳过了 season）。列顺序应按查询频率从高到低排：区分度高的放前面。

**Q: 唯一约束和唯一索引是一回事吗？**
> 在大多数数据库实现中等价——唯一约束会自动创建唯一索引。区别在于语义层面：唯一约束是"业务规则"（不允许重复），唯一索引是"性能优化"（加速查询顺便去重）。SQLAlchemy 里用 `UniqueConstraint` 表达业务约束，用 `Index(unique=True)` 表达索引意图。

## 5. ORM 关系映射（relationship）

### 概念

SQLAlchemy 的 `relationship()` 定义表与表之间的对象级关系，让开发者用属性访问关联数据，不用手写 JOIN。

```python
# 没有 relationship：
team = db.query(FantasyTeam).first()
drivers = db.query(FantasyTeamDriver).filter(FantasyTeamDriver.team_id == team.id).all()
# 要手动 JOIN 查关联

# 有 relationship：
team = db.query(FantasyTeam).first()
drivers = team.drivers   # 直接访问，ORM 自动查询
```

**关键参数**：

| 参数 | 作用 |
|------|------|
| `back_populates` | 双向关系，两边互相引用 |
| `cascade` | 级联操作（删除父记录时怎么处理子记录） |
| `lazy` | 加载策略（eager / lazy / select） |

```
cascade="all, delete-orphan"
  │
  ├── all = save-update + merge + refresh-expire + expunge + delete
  └── delete-orphan = 删除父记录时自动删除"孤儿"子记录
       User 删除 → 其 FantasyTeam 自动删除 → 其 Drivers/Constructors 自动删除
```

### 本项目代码（models.py —— 双向关系）

```python
class User(Base):
    # ...
    fantasy_teams = relationship("FantasyTeam", back_populates="user",
                                 cascade="all, delete-orphan")

class FantasyTeam(Base):
    # ...
    user = relationship("User", back_populates="fantasy_teams")
    drivers = relationship("FantasyTeamDriver", back_populates="team",
                           cascade="all, delete-orphan")
    constructors = relationship("FantasyTeamConstructor", back_populates="team",
                               cascade="all, delete-orphan")

class FantasyTeamDriver(Base):
    # ...
    team = relationship("FantasyTeam", back_populates="drivers")

class FantasyTeamConstructor(Base):
    # ...
    team = relationship("FantasyTeam", back_populates="constructors")
```

**关系链**：

```
User.fantasy_teams ──→ [FantasyTeam, FantasyTeam, ...]
                          │
                          ├── .user ──→ User（反向）
                          ├── .drivers ──→ [FantasyTeamDriver, ...]
                          │                  └── .team ──→ FantasyTeam（反向）
                          └── .constructors ──→ [FantasyTeamConstructor, ...]
                                                   └── .team ──→ FantasyTeam（反向）
```

**使用示例（main.py —— 查询阵容时直接访问关联数据）**：

```python
@app.get("/api/fantasy/team/{season}/{round}")
def get_my_fantasy_team(season: int, round: int, ...):
    team = db.query(models.FantasyTeam).filter(...).first()
    # team.drivers 和 team.constructors 是 ORM 自动查询的关联数据
    return {
        "drivers": [
            {"code": d.driver_code, "is_captain": d.is_captain, "price": d.price}
            for d in team.drivers    # ← 直接访问关联对象
        ],
        "constructors": [
            {"ref": c.constructor_ref, "price": c.price}
            for c in team.constructors  # ← 直接访问关联对象
        ],
    }
```

### 面试问答

**Q: `back_populates` 和 `backref` 的区别？**
> `back_populates` 需要两边都显式声明 `relationship`，代码更清晰但稍冗余。`backref` 只在一边声明，ORM 自动在另一边创建反向关系，简洁但"魔法"多。本项目用 `back_populates` 保证可读性。

**Q: 什么是 N+1 查询问题？怎么解决？**
> 访问 `team.drivers` 时 ORM 懒加载，每访问一个 team 就多查一次 drivers 表，查 N 个 team 会执行 1+N 次 SQL。解决方法：`relationship(..., lazy="joined")` 用 JOIN 一次查完，或 `db.query(Team).options(joinedload(Team.drivers)).all()`。本项目暂未优化，因为单次只查一个用户的阵容。

**Q: `cascade="all, delete-orphan"` 什么时候不该用？**
> 当子记录有独立生命周期时——比如 Order 和 Product，删除 Order 不应该删 Product。`delete-orphan` 只用于"子记录完全属于父记录"的场景（如 FantasyTeamDriver 完全属于 FantasyTeam）。

## 6. 配置管理与环境隔离

### 概念

项目配置（数据库 URL、密钥、规则参数）需要区分开发环境和生产环境。核心原则：**密钥不写死在代码里，通过环境变量注入**。

```
开发环境                        生产环境
┌──────────────────┐          ┌──────────────────────────────┐
│ SQLite 文件数据库  │          │ PostgreSQL 远程数据库        │
│ JWT_SECRET=默认值  │  ──→    │ JWT_SECRET=环境变量注入       │
│ FANTASY_BUDGET=100 │          │ FANTASY_BUDGET=100（不变）    │
└──────────────────┘          └──────────────────────────────┘
      ↑                              ↑
  config.py 读取               config.py 读取
  环境变量优先                    环境变量必填
```

### 本项目代码（config.py）

```python
import os

    # ── JWT 鉴权 ──
    JWT_SECRET = os.environ.get("JWT_SECRET", "f1-light-app-dev-secret-change-me")
    JWT_ALGORITHM = "HS256"
    JWT_EXPIRE_DAYS = 7

    # ── Ergast ──
    ERGAST_BASE_URL = "https://api.jolpi.ca/ergast/f1"

    # ── Fantasy 规则 ──
    FANTASY_BUDGET = 100.0       # 预算上限 ¥100M
    FANTASY_MAX_DRIVERS = 5
    FANTASY_MAX_CONSTRUCTORS = 2

    @property
    def connect_args(self):
        """SQLite 需要这个参数才能在多线程中使用"""
        if "sqlite" in self.DATABASE_URL:
            return {"check_same_thread": False}
        return {}


@lru_cache()
def get_settings():
    return Settings()

settings = get_settings()
```

**关键设计点**：

1. `os.environ.get("JWT_SECRET", "默认值")`：环境变量优先，没有则用默认值
2. `connect_args` 是 `@property`：根据 `DATABASE_URL` 动态返回不同参数
3. `@lru_cache()`：单例模式，整个应用只创建一个 Settings 实例

**SQLite 多线程问题**：

```python
# SQLite 默认只允许创建它的线程使用连接
# FastAPI 用线程池处理同步路由函数，多线程共享 Engine
# 如果不加 check_same_thread=False，会报：
# ProgrammingError: SQLite objects created in a thread can only be used in that same thread

connect_args={"check_same_thread": False}  # ← 允许跨线程使用
```

### 面试问答

**Q: 为什么不用 `.env` 文件 + python-dotenv？**
> 可以用，但本项目精简依赖。`os.environ.get()` 已经够用——开发用默认值，生产通过 `export JWT_SECRET=xxx` 或 Docker `ENV` 注入。如果配置项多了（>10个），建议用 `pydantic-settings` 自动加载 `.env`。

**Q: `@lru_cache()` 的作用是什么？**
> 缓存函数返回值，第二次调用直接返回缓存结果不再执行函数体。这里保证 `Settings()` 只实例化一次，避免重复解析环境变量。等价于单例模式，但更 Pythonic。

**Q: 切换到 PostgreSQL 需要改什么？**
> 只需改环境变量：`export DATABASE_URL=postgresql://user:pass@host:5432/f1app`。`connect_args` 会自动返回 `{}`（PostgreSQL 不需要 `check_same_thread`），ORM 代码零修改。这就是 ORM 跨数据库的优势。

## 7. bcrypt 密码哈希原理

### 概念

密码绝对不能明文存储。即使数据库被拖库，攻击者也无法还原明文密码。

```
明文密码 "mypassword123"
    │
    │  bcrypt 哈希（单向，不可逆）
    │  每次哈希随机生成 salt（盐）
    ↓
"$2b$12$N9qo8uLOickgx2ZMRZoMy.MrqK3a8vQvDg7B6YxD3.jDxvXvKm0Yi"
 ↑    ↑   ↑                    ↑
算法  cost salt(22字符)          哈希值(31字符)
$2b  12  N9qo8uLOickgx2ZMRZoMy  MrqK3a8vQvDg7B6YxD3.jDxvXvKm0Yi
```

**bcrypt vs MD5/SHA256**：

| 特性 | bcrypt | MD5/SHA256 |
|------|--------|-----------|
| 速度 | 慢（故意慢） | 快 |
| 盐 | 内置随机盐 | 需手动加 |
| 彩虹表 | 无法破解 | 可被彩虹表破解 |
| 暴力破解 | cost=12 约 0.3 秒/次 | 每秒数亿次 |
| 用途 | 密码存储 | 文件校验 |

**为什么 bcrypt 要"故意慢"？**
> 密码哈希的敌人是暴力破解。如果哈希很快，攻击者每秒能试 1 亿个密码；bcrypt cost=12 每次约 0.3 秒，每秒只能试 3 个，暴力破解不现实。正常用户登录多等 0.3 秒无所谓。

### 本项目代码（auth.py —— 直接使用 bcrypt 库）

```python
import bcrypt

def hash_password(password: str) -> str:
    """把明文密码转成 bcrypt 哈希。"""
    # 1. 编码为 bytes（bcrypt 操作的是 bytes 不是 str）
    pw_bytes = password.encode("utf-8")
    # 2. 截断到 72 字节（bcrypt 限制）
    pw_bytes = pw_bytes[:72]
    # 3. 生成随机 salt
    salt = bcrypt.gensalt()         # 默认 cost=12
    # 4. 哈希
    hashed = bcrypt.hashpw(pw_bytes, salt)
    # 5. 转回 str 存入数据库
    return hashed.decode("utf-8")


def verify_password(plain: str, hashed: str) -> bool:
    """验证密码是否匹配哈希值。"""
    try:
        return bcrypt.checkpw(
            plain.encode("utf-8")[:72],   # 明文转 bytes
            hashed.encode("utf-8")        # 哈希值转 bytes
        )
    except Exception:
        return False
```

**为什么不用 passlib？**（详见踩坑实录第 1 条）
> passlib 1.7.x 与 bcrypt 4.x 不兼容，`passlib` 内部调用 `bcrypt.__about__` 这个模块级变量，但 bcrypt 4.x 删掉了它，导致 `AttributeError`。本项目直接用 `bcrypt` 库，绕过 passlib 的兼容层。

### 面试问答

**Q: 为什么密码要截断到 72 字节？**
> bcrypt 算法设计上只处理前 72 字节的输入，超出的部分被忽略。如果不截断，72 字节之后的密码差异无法区分（"password123" 和 "password123456789" 的哈希可能相同）。显式截断是防御性编程。

**Q: bcrypt 哈希结果里包含了 salt，那验证时怎么拿到 salt？**
> bcrypt 哈希字符串格式 `$2b$12$salt22字符hash31字符` 自包含了算法版本、cost 和 salt。`bcrypt.checkpw()` 会从哈希字符串中解析出 salt，用它重新哈希明文，然后比较结果。所以不需要单独存 salt。

**Q: cost 因子设多少合适？**
> cost=12 是当前推荐值，每次哈希约 0.3 秒。cost 每增加 1，时间翻倍。随着硬件进步，应该定期提升 cost。但太高会让登录接口变慢，影响用户体验。本项目用默认 cost=12（`bcrypt.gensalt()` 默认 12）。

## 8. JWT 无状态鉴权

### 概念

JWT（JSON Web Token）是一种紧凑的、自包含的令牌格式，用于在客户端和服务端之间安全传输信息。

```
JWT 三段式：Header.Payload.Signature

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhZG1pbiIsInVzZXJfaWQiOjEsImV4cCI6MTcwMH0.abc123signature
         │                    │                                        │
         Header（算法）        Payload（数据）                           Signature（签名）
         {"alg":"HS256"}      {"sub":"admin","user_id":1,"exp":1700}   HMAC-SHA256(Header+Payload, SECRET)
```

**无状态鉴权 vs 有状态鉴权（Session）**：

| 对比项 | JWT（无状态） | Session（有状态） |
|--------|-------------|------------------|
| 服务端存储 | 不存，只验证签名 | 存 session 文件/Redis |
| 扩展性 | 天然支持水平扩展 | 需共享 session 存储 |
| 注销 | 困难（token 未过期前有效） | 简单（删 session） |
| 跨域 | 天然支持（放 Header） | 需 CORS + cookie 配置 |
| 安全性 | 签名防篡改，但 payload 可解码 | session 内容不可见 |

**鉴权流程**：

```
1. 用户登录：
   POST /api/auth/login {username, password}
   ← 服务器验证密码 → 签发 JWT → 返回 {access_token: "xxx"}

2. 客户端存储 token：
   localStorage.setItem("token", "xxx")

3. 后续请求带 token：
   GET /api/auth/me
   Header: Authorization: Bearer xxx

4. 服务器验证：
   解码 JWT → 检查签名 → 检查过期 → 取出 user_id → 查数据库 → 返回用户信息
```

### 本项目代码（auth.py —— JWT 签发与验证）

**签发 Token**：

```python
from jose import jwt, JWTError

def create_access_token(data: dict, expires_delta: Optional[timedelta] = None) -> str:
    """签发 JWT Token。"""
    to_encode = data.copy()
    # 设置过期时间
    expire = datetime.utcnow() + (expires_delta or timedelta(days=settings.JWT_EXPIRE_DAYS))
    to_encode.update({"exp": expire})
    # 用密钥签名编码
    return jwt.encode(to_encode, settings.JWT_SECRET, algorithm=settings.JWT_ALGORITHM)

# 使用示例：
token = create_access_token({"sub": user.username, "user_id": user.id})
# token = "eyJhbGciOiJIUzI1NiJ9.eyJzdWIi..."
```

**解码 Token**：

```python
def get_current_user(
    token: Optional[str] = Depends(oauth2_scheme),
    db: Session = Depends(get_db)
) -> User:
    """从 JWT 解析当前登录用户。"""
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="无法验证凭据，请先登录",
        headers={"WWW-Authenticate": "Bearer"},
    )
    if not token:
        raise credentials_exception
    try:
        # 解码 JWT（验证签名 + 检查过期）
        payload = jwt.decode(token, settings.JWT_SECRET,
                             algorithms=[settings.JWT_ALGORITHM])
        username: str = payload.get("sub")
        user_id: int = payload.get("user_id")
        if username is None or user_id is None:
            raise credentials_exception
    except JWTError:
        raise credentials_exception    # 签名错误或过期

    user = db.query(User).filter(User.id == user_id).first()
    if user is None:
        raise credentials_exception
    return user
```

**Token Payload 结构**：

```json
{
  "sub": "admin",          // subject = 用户名
  "user_id": 1,            // 自定义字段 = 用户 ID
  "exp": 1700000000        // expiration = 过期时间戳（自动添加）
}
```

### 面试问答

**Q: JWT 的 payload 是加密的吗？**
> 不是。payload 是 Base64URL 编码（不是加密），任何人都能解码看到内容。JWT 的安全保障是 Signature——防止篡改。如果 payload 含敏感信息（如密码），必须额外加密。本项目 payload 只放 username 和 user_id，不敏感。

**Q: JWT 过期后怎么办？能用 Refresh Token 吗？**
> JWT 过期后客户端需要重新登录。生产环境通常用双 Token 机制：Access Token（短期，如 15 分钟）+ Refresh Token（长期，如 7 天）。Access Token 过期后用 Refresh Token 换新的 Access Token，用户无感知。本项目简化设计，Access Token 直接 7 天过期。

**Q: 如果 JWT 被偷了怎么办？**
> JWT 在过期前一直有效，服务端无法主动作废（无状态的代价）。缓解措施：用 HTTPS 防中间人、token 过期时间设短、敏感操作二次验证、IP 绑定（token 里存 IP，解码后比对）。本项目用 HTTPS + 7 天过期，够用。

**Q: 为什么用 `python-jose` 而不是 `PyJWT`？**
> 两者功能类似。`python-jose` 额外支持 JWS/JWE/JWK 等完整 JOSE 标准。本项目选 jose 是因为 FastAPI 官方教程示例用 jose。如果只需基础 JWT，`PyJWT` 更轻量。

## 9. FastAPI 依赖注入鉴权

### 概念

FastAPI 的 `Depends()` 机制让鉴权代码极其简洁——路由函数声明 `user: User = Depends(get_current_user)`，FastAPI 自动完成 JWT 解码、用户查询，失败返回 401。

```
客户端请求
  │  Header: Authorization: Bearer eyJhbG...
  ↓
OAuth2PasswordBearer 提取 token
  │  从 Authorization 头解析 "Bearer xxx" → "xxx"
  ↓
get_current_user(token, db)
  │  解码 JWT → 查数据库 → 返回 User 对象
  ↓
路由函数收到 user 参数
  │  user.username, user.id 直接可用
  ↓
返回响应
```

**两种鉴权模式**：

| 模式 | 函数 | 无 Token 时 | 用途 |
|------|------|------------|------|
| 强制鉴权 | `get_current_user` | 401 Unauthorized | 登录才能用的接口 |
| 可选鉴权 | `get_optional_user` | 返回 None | 带登录信息体验更好，不登录也能用 |

### 本项目代码（auth.py —— OAuth2 方案）

```python
from fastapi.security import OAuth2PasswordBearer

# OAuth2 令牌提取器
# tokenUrl: Swagger 文档登录按钮指向的接口
# auto_error=False: 没 token 时不报错，返回 None（用于可选鉴权）
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/auth/login", auto_error=False)
```

**强制鉴权**（main.py）：

```python
@app.get("/api/auth/me")
def get_me(user: models.User = Depends(auth.get_current_user)):
    # ↑ 没登录 → 401；已登录 → user 对象注入
    return {
        "id": user.id,
        "username": user.username,
        "email": user.email,
    }
```

**可选鉴权**（auth.py）：

```python
def get_optional_user(
    token: Optional[str] = Depends(oauth2_scheme),
    db: Session = Depends(get_db)
) -> Optional[User]:
    """可选鉴权：带 token 就解析，没带就返回 None。"""
    if not token:
        return None
    try:
        payload = jwt.decode(token, settings.JWT_SECRET,
                             algorithms=[settings.JWT_ALGORITHM])
        user_id = payload.get("user_id")
        if user_id:
            return db.query(User).filter(User.id == user_id).first()
    except JWTError:
        pass
    return None    # token 无效不报错，返回 None
```

**注册接口完整流程（main.py）**：

```python
@app.post("/api/auth/register", response_model=schemas.TokenResponse)
def register(req: schemas.UserRegister, db: Session = Depends(get_db)):
    # 1. 检查用户名/邮箱是否已存在
    if db.query(models.User).filter(models.User.username == req.username).first():
        raise HTTPException(status_code=400, detail="用户名已存在")
    if db.query(models.User).filter(models.User.email == req.email).first():
        raise HTTPException(status_code=400, detail="邮箱已被注册")

    # 2. 创建用户（密码哈希存储）
    user = models.User(
        username=req.username,
        email=req.email,
        password_hash=auth.hash_password(req.password),  # bcrypt 哈希
    )
    db.add(user)
    db.commit()
    db.refresh(user)    # 获取数据库生成的 id

    # 3. 签发 JWT（注册即登录）
    token = auth.create_access_token({"sub": user.username, "user_id": user.id})
    return schemas.TokenResponse(
        access_token=token,
        username=user.username,
        user_id=user.id,
    )
```

**登录接口（main.py —— 支持用户名或邮箱）**：

```python
@app.post("/api/auth/login", response_model=schemas.TokenResponse)
def login(req: schemas.UserLogin, db: Session = Depends(get_db)):
    # 用 | (OR) 查询，支持用户名或邮箱登录
    user = db.query(models.User).filter(
        (models.User.username == req.username) | (models.User.email == req.username)

```

### 面试问答

**Q: `OAuth2PasswordBearer` 做了什么？**
> 它是一个依赖注入可调用对象，从 HTTP 请求的 `Authorization: Bearer <token>` 头中提取 token 字符串。`auto_error=False` 表示没找到 token 时不抛异常，返回 None。`tokenUrl` 只是 Swagger UI 的元数据，不影响实际行为。

**Q: 为什么登录接口不直接用 `OAuth2PasswordRequestForm`？**
> FastAPI 的 `OAuth2PasswordRequestForm` 要求 `application/x-www-form-urlencoded` 格式，而本项目用 JSON Body（`UserLogin` Pydantic 模型）。两者都能实现 OAuth2 密码模式，JSON 更方便前端处理。`tokenUrl` 指向 `/api/auth/login` 只是让 Swagger 文档的"Authorize"按钮能工作。

**Q: 多个依赖注入怎么组合？**
> `def create_team(req: schemas.FantasyTeamCreate, user: User = Depends(get_current_user), db: Session = Depends(get_db))`。FastAPI 会依次执行所有 `Depends()`，如果 `get_current_user` 抛 401，后续依赖不会执行，路由函数也不会执行。

## 10. Pydantic 请求模型与校验

### 概念

Pydantic 是 Python 的数据验证库，FastAPI 用它定义请求体和响应体的类型约束。

```
客户端 POST /api/auth/register
  Body: {"username": "ab", "email": "bad", "password": "123"}
       ↓
Pydantic 校验 UserRegister:
  username: min_length=3  ← "ab" 只有2位 → 校验失败
  email: 必须含 @ 和 .    ← "bad" 不含 → 校验失败
  password: min_length=6  ← "123" 只有3位 → 校验失败
       ↓
FastAPI 自动返回 422 Unprocessable Entity:
  {"detail": [{"loc": ["body", "username"], "msg": "..."}, ...]}
```

**Pydantic v2 的 `field_validator`**：

```python
from pydantic import BaseModel, Field, field_validator

class UserRegister(BaseModel):
    username: str = Field(..., min_length=3, max_length=50)
    email: str = Field(...)

    @field_validator("email")
    @classmethod
    def validate_email(cls, v):
        if "@" not in v or "." not in v:
            raise ValueError("邮箱格式不正确")
        return v
```

- `@field_validator("email")`：声明这是一个字段级验证器
- `@classmethod`：Pydantic v2 要求验证器是类方法
- `v`：字段值
- 返回值：验证通过后（可能修改）的值

### 面试问答

**Q: Pydantic v2 和 v1 有什么区别？**
> v2 用 Rust 重写核心（pydantic-core），性能提升 5-50 倍。API 变化：`@validator` → `@field_validator`，需要加 `@classmethod`；`class Config` → `model_config = ConfigDict(...)`；`.dict()` → `.model_dump()`。本项目用 v2 语法。

**Q: `Field(...)` 的 `...` 是什么？**
> Python 的 `Ellipsis` 对象（就是 `...`）。Pydantic 约定 `Field(...)` 表示"必填字段"——没有默认值，客户端必须传。`Field("none")` 表示"可选字段，默认值 none"。

**Q: Pydantic 模型和 SQLAlchemy ORM 模型有什么区别？为什么不混用？**
> Pydantic 模型用于 API 边界（请求/响应校验和序列化），SQLAlchemy 模型用于数据库（表结构映射）。混用会导致数据库字段暴露给客户端（如 password_hash），且 ORM 模型的懒加载属性在序列化时会触发意外查询。分离两者是"关注点分离"的最佳实践。

## 11. Fantasy 积分规则引擎

### 概念

Fantasy 游戏的积分规则是业务核心——根据比赛结果计算每个阵容的得分。规则来自 PRD 3.3.1：

```
车手积分 = 完赛积分 + 排位积分 + 最快圈加分 + 位置提升加分 + DNF 扣分
          × 队长加倍（如果选了队长）

车队积分 = 车队最好完赛名次对应积分
```

**积分规则表**：

| 规则 | 名次 → 积分 |
|------|-----------|
| 车手完赛 Top10 | 1→10, 2→8, 3→6, 4→5, 5→4, 6→3, 7→2, 8→1, 9→0, 10→0 |
| 车手排位 Top3 | 1→3, 2→2, 3→1 |
| 车队完赛 Top5 | 1→5, 2→4, 3→3, 4→2, 5→1 |
| 最快圈 | +5 |
| 位置提升 | 排位名次 - 完赛名次（正数才加分）× 1 |
| DNF | -5 |
| 队长加倍 | 车手积分 ×2 |

**芯片效果**：

| 芯片 | 效果 |
|------|------|
| `none` | 无 |
| `limitless` | 无预算限制（可超 ¥100M） |
| `no_negative` | DNF 不扣分 |
| `wildcard` | 换人不扣分（未实现） |

### 本项目代码（game_service.py —— 积分常量）

```python
# 完赛积分
FINISH_POINTS = {1: 10, 2: 8, 3: 6, 4: 5, 5: 4, 6: 3, 7: 2, 8: 1, 9: 0, 10: 0}

# 排位赛积分
QUALIFYING_POINTS = {1: 3, 2: 2, 3: 1}

# 车队完赛积分（取车队最好的名次）
CONSTRUCTOR_FINISH_POINTS = {1: 5, 2: 4, 3: 3, 4: 2, 5: 1}

# 最快圈加分
FASTEST_LAP_BONUS = 5

# DNF 扣分
DNF_PENALTY = -5
```

**单车手积分计算**：

```python
def calculate_driver_points(
    driver_code: str,
    finish_position: int,
    qualifying_position: int,
    is_fastest_lap: bool,
    status: str,
    is_captain: bool = False,
    chip: str = "none"
) -> dict:
    # 判断是否 DNF
    is_dnf = "Retired" in status or "Not Classified" in status or finish_position == 0

    # 1. 完赛积分
    finish_pts = FINISH_POINTS.get(finish_position, 0) if not is_dnf else 0

    # 2. 排位积分
    qual_pts = QUALIFYING_POINTS.get(qualifying_position, 0)

    # 3. 最快圈
    fastest_bonus = FASTEST_LAP_BONUS if is_fastest_lap else 0

    # 4. 位置提升（排位 → 正赛，每提升1位 +1）
    position_gain = 0
    if not is_dnf and qualifying_position and finish_position:
        gain = qualifying_position - finish_position
        if gain > 0:
            position_gain = gain    # 正数才加分（退位不扣分）

    # 5. DNF 扣分（no_negative 芯片抵消）
    dnf_penalty = 0
    if is_dnf:
        if chip == "no_negative":
            dnf_penalty = 0
        else:
            dnf_penalty = DNF_PENALTY

    # 汇总
    subtotal = finish_pts + qual_pts + fastest_bonus + position_gain + dnf_penalty

    # 队长加倍
    captain_bonus = subtotal if is_captain else 0
    total = subtotal + captain_bonus

    return {
        "code": driver_code,
        "finish_points": finish_pts,
        "qualifying_points": qual_pts,
        "fastest_lap_bonus": fastest_bonus,
        "position_gain": position_gain,
        "dnf_penalty": dnf_penalty,
        "subtotal": subtotal,
        "captain_bonus": captain_bonus,
        "total": total,
        "breakdown": "...",
    }
```

**计算示例**：

```
车手 VER，排位第 3，完赛第 1，拿了最快圈，选为队长：
  完赛积分 = FINISH_POINTS[1] = 10
  排位积分 = QUALIFYING_POINTS[3] = 1
  最快圈 = 5
  位置提升 = 3 - 1 = 2 → +2
  DNF 扣分 = 0
  小计 = 10 + 1 + 5 + 2 + 0 = 18
  队长加倍 = 18 × 2 = 36
  总分 = 18 + 18 = 36

车手 HAM，排位第 1，DNF：
  完赛积分 = 0（DNF）
  排位积分 = QUALIFYING_POINTS[1] = 3
  最快圈 = 0
  位置提升 = 0（DNF 不算）
  DNF 扣分 = -5
  小计 = 0 + 3 + 0 + 0 + (-5) = -2
  总分 = -2
```

**阵容总分聚合（game_service.py）**：

```python
def calculate_team_points(
    team_drivers: list[dict],
    team_constructors: list[dict],
    race_results: list[dict],      # Ergast 原始结果
    fastest_lap_driver: str,
    chip: str = "none"
) -> dict:
    # 构建车手名次映射
    driver_map = {}
    for r in race_results:
        code = r.get("Driver", {}).get("code", "")
        if code:
            driver_map[code] = r

    # 构建车队名次映射（取车队最好的名次）
    constructor_map = {}
    for r in race_results:
        cref = r.get("Constructor", {}).get("constructorId", "")
        pos = int(r.get("position", 999))
        if cref and (cref not in constructor_map or pos < constructor_map[cref]):
            constructor_map[cref] = pos

    # 计算每个车手
    driver_details = []
    for pick in team_drivers:
        code = pick["driver_code"]
        race_data = driver_map.get(code, {})
        detail = calculate_driver_points(
            driver_code=code,
            finish_position=int(race_data.get("position", 0)),
            qualifying_position=int(race_data.get("grid", 0)),  # grid = 发车位
            is_fastest_lap=(code == fastest_lap_driver),
            status=race_data.get("status", "Retired"),
            is_captain=pick.get("is_captain", False),
            chip=chip
        )
        driver_details.append(detail)

    # 计算每个车队
    constructor_details = []
    for pick in team_constructors:
        ref = pick["constructor_ref"]
        best_pos = constructor_map.get(ref, 0)
        detail = calculate_constructor_points(ref, best_pos)
        constructor_details.append(detail)

    total = sum(d["total"] for d in driver_details) + \
            sum(c["total"] for c in constructor_details)

    return {
        "total_points": total,
        "driver_details": driver_details,
        "constructor_details": constructor_details,
    }
```

### 面试问答

**Q: 为什么用字典 `FINISH_POINTS = {1: 10, ...}` 而不是 if-else？**
> 字典查表 O(1)，代码简洁可读。`FINISH_POINTS.get(finish_position, 0)` 一步完成"查表 + 默认值"。用 if-else 要写 10 个分支，改规则时要改多处。字典也方便序列化为 JSON 传给前端展示规则。

**Q: `position_gain` 为什么只加分不扣分？**
> 设计决策：鼓励"上升"但不惩罚"下降"——退位已经损失了完赛积分（名次低了积分少），再扣分会让阵容分数偏低。这是 Fantasy 游戏常见设计：奖励正面表现，不双重惩罚负面表现。

**Q: 队长加倍为什么加倍"小计"而不是加倍"完赛积分"？**
> 加倍小计 = 加倍所有正面和负面分（完赛 + 排位 + 最快圈 + 位置提升 + DNF 扣分）。这让队长选择更有策略性：选稳定拿分的车手当队长（收益最大化），但如果队长 DNF，扣分也翻倍——风险与收益并存。

## 12. Fantasy 阵容预算校验

### 概念

Fantasy 游戏的核心约束：预算有限（¥100M），车手和车队有不同价格，玩家要在预算内组建最优阵容。

```
预算校验规则：
  1. 车手数量 ≤ 5
  2. 车队数量 ≤ 2
  3. 总花费 ≤ ¥100M（除非用了 limitless 芯片）

示例：
  VER (25M) + NOR (20M) + LEC (18M) + ALO (15M) + STR (10M) = 88M（车手）
  Red Bull (15M) + Ferrari (12M) = 27M（车队）
  总计 = 88 + 27 = 115M > 100M → 校验失败！

  如果用 limitless 芯片 → 校验通过（无预算限制）
```

### 本项目代码（game_service.py —— validate_team_budget）

```python
BUDGET_LIMIT = 100.0
MAX_DRIVERS = 5
MAX_CONSTRUCTORS = 2

def validate_team_budget(
    drivers: list[dict],
    constructors: list[dict],
    chip: str = "none"
) -> tuple[bool, float, str]:
    """校验阵容预算是否超标。

    返回：(是否合法, 总花费, 错误信息)
    """
    # 1. 检查车手数量
    if len(drivers) > MAX_DRIVERS:
        return False, 0, f"车手数量超出限制（最多{MAX_DRIVERS}个）"

    # 2. 检查车队数量
    if len(constructors) > MAX_CONSTRUCTORS:
        return False, 0, f"车队数量超出限制（最多{MAX_CONSTRUCTORS}个）"

    # 3. 计算总花费
    total = sum(d["price"] for d in drivers) + sum(c["price"] for c in constructors)

    # 4. limitless 芯片跳过预算检查
    if chip == "limitless":
        return True, total, "Limitless 芯片：无预算限制"

    # 5. 预算超标检查
    if total > BUDGET_LIMIT:
        return False, total, f"预算超标：¥{total:.1f}M > ¥{BUDGET_LIMIT}M"

    return True, total, ""
```

```python
@app.post("/api/fantasy/team")
def create_fantasy_team(
    req: schemas.FantasyTeamCreate,
    user: models.User = Depends(auth.get_current_user),
    db: Session = Depends(get_db)
):
    # 校验阵容
    valid, total_cost, msg = game_service.validate_team_budget(
        [{"driver_code": d.driver_code, "price": d.price} for d in req.drivers],
        [{"constructor_ref": c.constructor_ref, "price": c.price} for c in req.constructors],
        req.chip
    )
    if not valid:
        raise HTTPException(status_code=400, detail=msg)

    # 检查是否已有阵容（每人每站一份）
    existing = db.query(models.FantasyTeam).filter(
        models.FantasyTeam.user_id == user.id,
        models.FantasyTeam.season == req.season,
        models.FantasyTeam.round == req.round
    ).first()

    if existing:
        # 更新：先删旧关联
        db.query(models.FantasyTeamDriver).filter(
            models.FantasyTeamDriver.team_id == existing.id
        ).delete()
        db.query(models.FantasyTeamConstructor).filter(
            models.FantasyTeamConstructor.team_id == existing.id
        ).delete()
        team = existing
        team.chip_used = req.chip
        team.total_cost = total_cost
    else:
        # 新建
        team = models.FantasyTeam(
            user_id=user.id, season=req.season, round=req.round,
            chip_used=req.chip, total_cost=total_cost,
        )
        db.add(team)
        db.flush()    # flush 后 team.id 有值

    # 写入车手
    for pick in req.drivers:
        db.add(models.FantasyTeamDriver(
            team_id=team.id, driver_code=pick.driver_code,
            is_captain=pick.is_captain, price=pick.price
        ))

    # 写入车队
    for pick in req.constructors:
        db.add(models.FantasyTeamConstructor(
            team_id=team.id, constructor_ref=pick.constructor_ref, price=pick.price
        ))

    db.commit()
    db.refresh(team)
    return {"id": team.id, "message": "阵容保存成功"}
```

### 面试问答

**Q: 更新阵容时为什么要先删旧关联再写新的？**
> 因为关联表（FantasyTeamDriver / FantasyTeamConstructor）没有 upsert 逻辑。直接 `db.add()` 新关联会导致 team_id + driver_code 唯一约束冲突（如果用户没换车手）。先 `delete()` 旧关联再 `add()` 新关联是最简单的方案。也可以用 `merge()` 但语义不如删除+重建清晰。

**Q: `db.flush()` 和 `db.commit()` 都在本函数里调用，为什么？**
> `flush()` 把 FantasyTeam 对象写入数据库（但不提交事务），执行后 `team.id` 由数据库自增生成。后续写 FantasyTeamDriver 时需要 `team.id` 做外键，所以必须先 flush。最后 `commit()` 统一提交所有操作，保证原子性——如果写车手时出错，flush 的数据也会回滚。

**Q: 返回 `tuple[bool, float, str]` 有什么好处？**
> 一次调用拿到所有信息：是否合法、总花费（合法也要返回给前端展示）、错误信息。比抛异常更灵活——调用方可以根据 `bool` 决定走正常流程还是返回错误，不用 try/except。这是 Python 函数式编程风格。

## 13. Fantasy 动态定价算法

### 概念

车手和车队的价格不是固定的，而是根据赛季表现动态调整。表现好的车手价格高，表现差的价格低，模拟真实 F1 Fantasy 游戏的定价机制。

```
driver_price = base_price × (0.5 + 0.5 × season_points_ratio) + trend_bonus - dnf_penalty

base_price 由上赛季排名决定：
  Top 3  → 30M
  Top 5  → 25M
  Top 10 → 20M
  其余   → 15M
  新秀   → 10M

season_points_ratio = 当前积分 / 赛季最高积分（0-1）

trend_bonus = max(0, 15 - 近期平均名次) × 0.5
  近期平均名次 1 → +7.0M（表现极佳）
  近期平均名次 10 → +2.5M
  近期平均名次 15+ → +0M

dnf_penalty = min(DNF次数 × 2, 10)
  每次退赛扣 2M，最多扣 10M
```

**设计思路**：

```
                    base_price（上赛季排名）
                    × (0.5 + 0.5 × ratio)（本赛季状态）
                    + trend（近期手感）
                    - penalty（可靠性惩罚）
                    ↓
                    最终价格（最低 5M）
```

- **基础价**占 50%：上赛季排名是车手价值的"底"
- **赛季状态**占 50%：当前赛季积分占比越高，价格越接近 base × 1.0
- **趋势加成**：近期手感好涨价
- **DNF 惩罚**：退赛多降价

### 本项目代码（game_service.py —— calculate_driver_price）

```python
def calculate_driver_price(
    season_points: float = 0,
    max_season_points: float = 600,
    recent_avg_position: float = 10,
    dnf_count: int = 0,
    last_season_rank: int = 0,
) -> float:
    """动态定价算法。返回价格（M，百万）。"""
    # 1. 基础价（由上赛季排名决定）
    if last_season_rank <= 3:
        base = 30
    elif last_season_rank <= 5:
        base = 25
    elif last_season_rank <= 10:
        base = 20
    elif last_season_rank > 0:
        base = 15
    else:
        base = 10    # 新秀（rank=0 表示上赛季未参赛）

    # 2. 赛季积分占比（0-1）
    ratio = min(1.0, season_points / max(max_season_points, 1))
    # ratio=0.5 → 价格 = base × (0.5 + 0.5×0.5) = base × 0.75
    # ratio=1.0 → 价格 = base × (0.5 + 0.5×1.0) = base × 1.0

    # 3. 趋势加成：近期平均名次越低（越好）价格越高
    trend = max(0, (15 - recent_avg_position)) * 0.5
    # avg_pos=1 → trend = 14 × 0.5 = 7.0
    # avg_pos=15 → trend = 0

    # 4. DNF 惩罚：每次 -2M，最多 -10M
    penalty = min(dnf_count * 2, 10)

    # 5. 计算最终价格
    price = base * (0.5 + 0.5 * ratio) + trend - penalty
    return round(max(5.0, price), 1)   # 最低 5M，保留1位小数
```

**计算示例**：

```
VER：上赛季排名第1，本赛季积分450/600=0.75，近期平均名次2.0，0次DNF
  base = 30
  ratio = 0.75
  price_before_trend = 30 × (0.5 + 0.5×0.75) = 30 × 0.875 = 26.25
  trend = (15-2) × 0.5 = 6.5
  penalty = 0
  price = 26.25 + 6.5 - 0 = 32.75 → 32.8M

LAT：上赛季排名第18，本赛季积分20/600=0.03，近期平均名次16，2次DNF
  base = 15
  ratio = 0.033
  price_before_trend = 15 × (0.5 + 0.5×0.033) = 15 × 0.517 = 7.75
  trend = max(0, 15-16) × 0.5 = 0
  penalty = min(2×2, 10) = 4
  price = 7.75 + 0 - 4 = 3.75 → max(5.0, 3.75) = 5.0M（触底保护）
```

### 面试问答

**Q: 为什么用 `min(1.0, ratio)` 限制 ratio 不超过 1？**
> 如果某车手赛季积分超过 `max_season_points`（如 max 设 600 但实际积了 650），ratio > 1 会导致价格超过 base。`min(1.0, ratio)` 确保价格不会超过 base 的 100%。这是防御性编程——参数边界保护。

**Q: `max(5.0, price)` 触底保护为什么是 5M？**
> 游戏设计决策。如果价格降到 0 甚至负数，玩家可以免费选一堆低分车手。设最低 5M 保证所有车手都有成本，预算约束始终有效。5M 是经验值，可调。

**Q: 这个定价算法和机器学习定价有什么区别？**
> 规则定价（本项目）用手工设计的公式，可解释、可调参，但依赖人工经验。机器学习定价可以用历史交易数据训练回归模型，自动学习价格与表现的关系，但需要大量数据且可解释性差。本项目先用规则版跑通，后续可替换为 ML 版。

## 14. 规则加权预测模型

### 概念

AI 预测不一定要用深度学习。本项目用**规则加权模型**（rule-based weighted model），用 5 个特征手工设定权重，输出夺冠概率分布。

```
为什么不用 XGBoost / 深度学习？
  1. 训练 XGBoost 需要先采集 2018-2025 全部历史数据 + 特征工程
  2. 在线推理先用规则模型跑通端到端流程
  3. 规则模型的特征维度与 XGBoost 版本保持一致
  4. 后续训练完模型后，只需替换 predict_race() 的实现即可无缝切换

规则模型 = 特征 × 权重 → 归一化 → 概率分布
```

**5 个特征及权重**：

| 特征 | 含义 | 权重 | 理由 |
|------|------|------|------|
| championship_ratio | 赛季积分占比 | 35% | 赛季状态最强信号 |
| recent_avg_pos | 近5场平均完赛位次 | 25% | 近期手感 |
| qualifying_pos | 排位赛位次 | 15% | 发车位置影响大 |
| win_rate | 历史胜率 | 15% | 职业生涯统治力 |
| dnf_rate | 近期 DNF 率 | 10% | 可靠性扣分 |

### 本项目代码（prediction_service.py —— 数据获取）

```python
ERGAST_BASE = "https://api.jolpi.ca/ergast/f1"
```

```python
def _calculate_features(standings, recent, qualifying, total_rounds) -> list:
    """为每位车手计算特征向量。"""
    if not standings:
        return []

    max_points = max(d["points"] for d in standings) or 1

    features = []
    for driver in standings:
        code = driver["code"]

        # 1. 赛季积分占比（0-1）
        championship_ratio = driver["points"] / max_points if max_points > 0 else 0

        # 2. 近5场平均完赛位次
        positions = []
        dnf_count = 0
        for race in recent:
            for r in race["results"]:
                if r["code"] == code:
                    pos = r["position"]
                    if pos > 0:
                        positions.append(pos)
                    if "Retired" in r["status"] or pos == 0:
                        dnf_count += 1
                    break

        recent_avg_pos = sum(positions) / len(positions) if positions else 20
        dnf_rate = dnf_count / len(recent) if recent else 0

        # 3. 排位赛位次
        qual_pos = qualifying.get(code, 20)

        # 4. 历史胜率（本赛季）
        win_rate = driver["wins"] / max(total_rounds, 1)

        features.append({
            "code": code,
            "name": driver["name"],
            "constructor": driver["constructor"],
            "features": {
                "championship_ratio": round(championship_ratio, 4),
                "recent_avg_pos": round(recent_avg_pos, 2),
                "qualifying_pos": qual_pos,
                "win_rate": round(win_rate, 4),
                "dnf_rate": round(dnf_rate, 4),
            }
        })
    return features
```

### 面试问答

**Q: 规则模型和机器学习模型的本质区别是什么？**
> 规则模型的权重是人工设定的（35%, 25%, ...），机器学习模型的权重是数据驱动学习的。规则模型不需要训练数据，上线快、可解释，但精度有上限。机器学习模型需要训练数据，精度通常更高，但黑盒不可解释。本项目先用规则模型跑通流程，后续可替换为 XGBoost。

**Q: 为什么取近 5 场而不是近 3 场或近 10 场？**
> 5 场是经验值——太少（3场）波动大，不能反映稳定状态；太多（10场）包含了很久以前的状态，可能不反映当前手感。F1 Fantasy 官方也用近 5 场作为"近期表现"窗口。

**Q: `max_points = max(d["points"] for d in standings) or 1` 的 `or 1` 是什么意思？**
> 如果所有车手积分都是 0（赛季刚开始），`max(...)` 返回 0，`0 or 1` = 1，避免除零错误。这是 Python 短路求值技巧：`0` 是 falsy，`or` 返回右边的 `1`。

## 15. 特征工程与归一化

### 概念

不同特征的量纲不同——积分占比是 0-1，平均名次是 1-20，胜率是 0-1。加权前必须统一归一化到 0-1 区间，否则量纲大的特征会"淹没"量纲小的特征。

```
归一化前：
  championship_ratio = 0.75    （0-1 区间）
  recent_avg_pos = 3.5         （1-20 区间）← 量纲不同！
  qualifying_pos = 2            （1-20 区间）

直接加权 → 名次特征（值大）会淹没积分特征

归一化后（全部 0-1）：
  championship_ratio → 0.75     （已经是 0-1）
  recent_avg_pos → 0.86         （(20-3.5)/19 ≈ 0.86，越低越好→分数越高）
  qualifying_pos → 0.89         （(20-2)/19 ≈ 0.89）
```

**名次归一化公式**：

```
score = max(0, 1 - (position - 1) / 19)

position=1  → score=1.0   （最好）
position=10 → score=0.53
position=20 → score=0.05   （最差）
```

### 本项目代码（prediction_service.py —— _weighted_score）

```python
def _weighted_score(features: dict) -> float:
    """计算加权得分，输出原始分数（未归一化）。"""
    fr = features["features"]

    # 1. 积分占比：0-1 → 直接用
    champ_score = fr["championship_ratio"]

    # 2. 近期平均位次：1=最好 → 转成 0-1（越低越好→分数越高）
    recent_score = max(0, 1 - (fr["recent_avg_pos"] - 1) / 19)
    # pos=1 → 1-(0/19) = 1.0
    # pos=20 → 1-(19/19) = 0.0

    # 3. 排位位次：同上公式
    qual_score = max(0, 1 - (fr["qualifying_pos"] - 1) / 19)

    # 4. 胜率：直接 0-1，但放大（2场胜利=1.0）
    win_score = min(1.0, fr["win_rate"] * 5)
    # win_rate=0.2 → 0.2×5=1.0（封顶）
    # win_rate=0.1 → 0.1×5=0.5

    # 5. DNF 率：0=好 → 1.0，1=差 → 0.0
    dnf_score = 1 - fr["dnf_rate"]

    # 加权求和
    raw = (
        champ_score * 0.35    # 35%
        + recent_score * 0.25  # 25%
        + qual_score * 0.15    # 15%
        + win_score * 0.15     # 15%
        + dnf_score * 0.10      # 10%
    )
    return raw
```

**特征权重可视化**：

```
                    权重分配
    ┌──────────────────────────────────────────┐
    │ championship_ratio  ██████████████████ 35% │
    │ recent_avg_pos      █████████████ 25%      │
    │ qualifying_pos      ████████ 15%            │
    │ win_rate            ████████ 15%            │
    │ dnf_rate            █████ 10%               │
    └──────────────────────────────────────────┘
                     ↓
              raw_score (0-1)
```

**计算示例（VER）**：

```
VER 特征：
  championship_ratio = 0.85   → champ_score = 0.85
  recent_avg_pos = 2.5        → recent_score = 1-(1.5/19) = 0.92
  qualifying_pos = 1          → qual_score = 1-(0/19) = 1.0
  win_rate = 0.4              → win_score = min(1.0, 0.4×5) = 1.0
  dnf_rate = 0.0             → dnf_score = 1-0 = 1.0

raw_score = 0.85×0.35 + 0.92×0.25 + 1.0×0.15 + 1.0×0.15 + 1.0×0.10
          = 0.2975 + 0.23 + 0.15 + 0.15 + 0.10
          = 0.9275
```

### 面试问答

**Q: 为什么胜率要乘 5 放大？**
> F1 一个赛季约 20-24 场，即使最 dominant 的车手胜率也很难超过 50%（如 12 胜 / 24 场 = 0.5）。如果不放大，胜率特征贡献最多 0.5×0.15=0.075，与其他特征相比太小。乘 5 后，4 场胜利（4/24≈0.17）×5≈0.83，与其他特征量级匹配。

**Q: Min-Max 归一化和 Z-Score 标准化有什么区别？**
> Min-Max：`(x-min)/(max-min)` → 结果在 [0,1]，适合已知上下界的场景（名次 1-20）。Z-Score：`(x-mean)/std` → 结果均值 0 标准差 1，适合正态分布数据。本项目用 Min-Max（手动设定上下界 1-20），因为 F1 名次有明确的物理范围。

**Q: 如果某个特征缺失（如新车手没有历史数据）怎么办？**
> 本项目用默认值兜底：`qualifying.get(code, 20)` 排位缺失默认第 20 位，`recent_avg_pos` 没有数据默认 20。这会让新车手得分偏低，符合"没有数据证明实力就给低分"的保守策略。更精细的做法是用同车队车手数据或历史新秀平均值填充。

## 16. Softmax 概率归一化

### 概念

加权得分是原始分数（0-1），但不是概率（所有车手概率之和应该等于 1）。需要归一化为概率分布。

```
原始分数：VER=0.93, NOR=0.75, LEC=0.68, HAM=0.60, ...（20 个车手）
                                          总和 = 12.5

归一化：probability = raw_score / sum(all_raw_scores)

VER 概率 = 0.93 / 12.5 = 0.074
NOR 概率 = 0.75 / 12.5 = 0.060
...
所有概率之和 = 1.0
```

**为什么不是真正的 Softmax？**
> 真正的 Softmax 是 `e^xi / Σ(e^xj)`，用指数函数放大差异。本项目用的是**线性归一化**（`xi / Σxj`），更简单直观。差异在于：Softmax 会让高分车手概率更高（指数放大），线性归一化保持原始比例。

### 本项目代码（prediction_service.py —— predict_race）

```python
def predict_race(year: int, round_num: int) -> dict:
    """预测指定分站的夺冠概率分布。"""
    try:
        # 1. 获取数据
        standings = _fetch_driver_standings(year)
        if not standings:
            return {"code": 500, "msg": f"无法获取 {year} 赛季车手积分榜"}

        recent = _fetch_recent_results(year, round_num, count=5)
        qualifying = _fetch_qualifying(year, round_num)

        # 2. 计算特征
        features_list = _calculate_features(standings, recent, qualifying, round_num - 1)

        # 3. 加权打分
        scored = []
        for f in features_list:
            raw = _weighted_score(f)
            scored.append({
                "driver_code": f["code"],
                "driver_name": f["name"],
                "constructor": f["constructor"],
                "features": f["features"],
                "raw_score": round(raw, 4),
            })

        # 4. 归一化为概率（线性归一化，非真正 softmax）
        total_raw = sum(s["raw_score"] for s in scored)
        if total_raw == 0:
            # 所有分数为 0，均分
            for s in scored:
                s["probability"] = round(1.0 / len(scored), 4)
        else:
            for s in scored:
                s["probability"] = round(s["raw_score"] / total_raw, 4)

        # 5. 排序 + 排名
        scored.sort(key=lambda x: x["probability"], reverse=True)
        for i, s in enumerate(scored, 1):
            s["rank_pred"] = i

        top3 = [s["driver_code"] for s in scored[:3]]

        return {
            "code": 200,
            "season": year,
            "round": round_num,
            "model_version": "rule_v1",
            "feature_count": 5,
            "feature_weights": {
                "championship_ratio": 0.35,
                "recent_avg_pos": 0.25,
                "qualifying_pos": 0.15,
                "win_rate": 0.15,
                "dnf_rate": 0.10,
            },
            "predictions": scored,
            "top3": top3,
        }

    except Exception as e:
        return {"code": 500, "msg": f"预测服务异常: {e}"}
```

```json

  "predictions": [

    {"driver_code": "NOR", "probability": 0.068, "rank_pred": 2, "raw_score": 0.75},
```

### 面试问答

**Q: 线性归一化和 Softmax 有什么区别？什么时候用哪个？**
> 线性归一化 `xi/Σxj` 保持原始比例，差异温和。Softmax `e^xi/Σe^xj` 用指数放大差异，高分项概率更高。当原始分数差异小（如都集中在 0.6-0.9）时，Softmax 能放大差异让 Top 车手概率更突出；当差异已经大时，线性归一化更直观。本项目用线性归一化，简单够用。

**Q: `total_raw == 0` 的分支什么时候触发？**
> 当所有车手的 `raw_score` 都是 0 时——极端情况，如赛季刚开始、所有人积分为 0、没有近期比赛数据。此时均分概率 `1/N` 给每个车手，避免除零错误。

**Q: 预测结果怎么存入数据库？**
> `Prediction` 表有 `features_json` 字段存特征快照。当前 `predict_race()` 直接返回结果，没自动存库。可以加一个函数在预测后批量写入：`for s in scored: db.add(Prediction(season=year, round=round, driver_code=s["driver_code"], probability=s["probability"], rank_pred=s["rank_pred"], features_json=json.dumps(s["features"])))`。

```python
@app.post("/api/vote", summary="最佳车手投票")
def cast_vote(
    req: schemas.VoteCreate,
    user: models.User = Depends(auth.get_current_user),
    db: Session = Depends(get_db)
):
    # 先查是否已投票（利用唯一约束防重复）
    existing = db.query(models.Vote).filter(
        models.Vote.user_id == user.id,
        models.Vote.season == req.season,
        models.Vote.round == req.round,
        models.Vote.vote_type == "driver_of_day"
    ).first()

    if existing:
        # 已投过 → 更新投票选择
        existing.driver_code = req.driver_code
        existing.voted_at = datetime.utcnow()
        db.commit()
        return {"message": "投票已更新", "driver_code": req.driver_code}
    else:
        # 没投过 → 新建
        vote = models.Vote(
            user_id=user.id,
            season=req.season,
            round=req.round,
            driver_code=req.driver_code,
        )
        db.add(vote)
        db.commit()
        return {"message": "投票成功", "driver_code": req.driver_code}
```

### 面试问答

**Q: `func.count()` 和 `len(results)` 有什么区别？**
> `func.count()` 在数据库层面统计行数（SQL `COUNT(*)`），只返回一个数字。`len(results)` 是把所有行查出来再在 Python 层面数。当数据量大时，`COUNT(*)` 只传一个数字，网络开销小；`len()` 传输所有行，浪费带宽。聚合统计永远用 `func.count()`。

**Q: `.label("vote_count")` 的作用是什么？**
> 给聚合列起别名。查询结果 `r` 是一个 Row 对象，`r[1]` 可以按位置取值，`r.vote_count` 可以按别名取值。等价于 SQL 的 `COUNT(*) AS vote_count`。取别名让代码更可读。

**Q: 投票更新时为什么要手动设 `voted_at = datetime.utcnow()`？**
> SQLAlchemy 的 `default=datetime.utcnow` 只在 INSERT 时生效，UPDATE 时不自动更新。如果需要"修改时间"自动更新，要用 `onupdate=datetime.utcnow` 参数。本项目手动设 `voted_at` 因为只有投票更新接口需要改这个字段。

## 18. 项目踩坑实录

### 踩坑 1：passlib + bcrypt 版本不兼容

**现象**：
```
AttributeError: module 'bcrypt' has no attribute '__about__'
```

**根因**：
passlib 1.7.x 内部通过 `bcrypt.__about__.__version__` 获取 bcrypt 版本号。但 bcrypt 4.0+ 删除了 `__about__` 模块（改用 `bcrypt.__version__`），导致 passlib 找不到属性而崩溃。

**排查过程**：
1. 搜索报错信息，发现是 passlib + bcrypt 4.x 的已知兼容问题
2. passlib 最后一次更新在 2020 年，长期不维护
3. 降级 bcrypt 到 3.x 可以修复，但不想用旧版

**修复**：直接用 bcrypt 库，绕过 passlib

```python
# ❌ 之前（passlib 方式）
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
hash = pwd_context.hash(password)
ok = pwd_context.verify(password, hash)

# ✅ 修复后（直接用 bcrypt）
import bcrypt
def hash_password(password: str) -> str:
    pw_bytes = password.encode("utf-8")[:72]
    salt = bcrypt.gensalt()
    return bcrypt.hashpw(pw_bytes, salt).decode("utf-8")

def verify_password(plain: str, hashed: str) -> bool:
    return bcrypt.checkpw(plain.encode("utf-8")[:72], hashed.encode("utf-8"))
```

**教训**：
- 依赖间接库（passlib 封装 bcrypt）增加了一层抽象，一旦上游不维护就会出问题
- 能直接用底层库就直接用，减少中间层

### 踩坑 2：FantasyTeam.vue 拼写错误 captianCode → captainCode

**现象**：
前端 Fantasy 阵容页面，队长加倍功能不生效。队长选了 VER，但积分没有翻倍。

```javascript
const captianPick = this.drivers.find(d => d.code === this.captianCode);

// ✅ 修复

if (pick.is_captain) this.captainCode = pick.driver_code;
const captainPick = this.drivers.find(d => d.code === this.captainCode);
```

1. 后端日志显示 `is_captain: false`，说明前端没传队长标记

### 踩坑 3：main.py 中 round 参数遮蔽内置函数

**现象**：
`get_vote_results` 函数里 `round()` 报错：
```
TypeError: 'int' object is not callable
```

**根因**：
路由函数参数名 `round` 遮蔽了 Python 内置函数 `round()`：

```python
# ❌ 问题代码
@app.get("/api/vote/results/{season}/{round_num}")
def get_vote_results(season: int, round_num: int, db: Session = Depends(get_db)):
    # ...
    "percentage": round(int(r[1]) / total * 100, 1) if total > 0 else 0,
    #           ↑ round 在这个作用域里被参数 round_num 遮蔽了吗？
    #           实际上 round_num 没遮蔽 round()，但其他函数用了 round 做参数名
```

实际上问题出在其他路由函数：

```python
# ❌ 这些路由用 round 做参数名
@app.get("/api/fastf1/{year}/{round}/fast-lap")
def get_fastf1_fastest_lap(year: int, round: int, session_type: str = 'R'):
    return fetch_fastf1_fastest_lap(year, round, session_type)
    #                               ↑ round 在这里被参数遮蔽

@app.get("/api/prediction/{year}/{round}")
def get_prediction(year: int, round: int):
    result = prediction_service.predict_race(year, round)
    #                                                    ↑ 传入的是 int 值，没问题
```

**修复**：将路径参数 `round` 统一改为 `round_num`

```python
# ✅ 修复后
@app.get("/api/fastf1/{year}/{round}/fast-lap")
def get_fastf1_fastest_lap(year: int, round: int, session_type: str = 'R'):
    # 路径参数名保持 round（URL 不变），但函数内部用 round_num
    return fetch_fastf1_fastest_lap(year, round, session_type)
```

实际修复方案是在 `get_vote_results` 中避免 `round()` 调用被影响，确保参数名不与内置函数冲突：

```python
# ✅ 投票结果函数中，round_num 作为参数名，round() 内置函数可用
@app.get("/api/vote/results/{season}/{round_num}")
def get_vote_results(season: int, round_num: int, db: Session = Depends(get_db)):
    # round_num 不遮蔽 round()，所以 round() 可以正常调用

```

**教训**：
- Python 没有块级作用域，函数参数会遮蔽同名的内置函数/模块
- 不要用 `round`、`list`、`dict`、`type`、`id`、`input` 等内置名做变量名
- 用 `round_num` / `round_number` 等带后缀的名字更安全

### 踩坑 4：voted_at 默认值读取失败

**现象**：
投票更新接口报错：
```
AttributeError: Neither 'Column' object nor 'Comparator' object has an attribute 'arg'
```

**根因**：
尝试通过 ORM 元数据读取 `voted_at` 的默认值：

```python
# ❌ 错误写法
existing.voted_at = models.Vote.__table__.c.voted_at.default.arg()
```

`Column.default` 是一个 `ColumnDefault` 对象，不是直接可调用的。`.arg` 是它的内部属性，不一定存在，直接调用会报错。

**修复**：直接用 `datetime.utcnow()`

```python
# ✅ 修复后
from datetime import datetime
existing.voted_at = datetime.utcnow()
```

**教训**：
- 不要通过 ORM 元数据反射来获取默认值，直接调用原始函数更简单可靠
- `default=datetime.utcnow` 的语义是"INSERT 时自动调用这个函数"，手动更新时不触发
- 如果需要"每次修改都更新时间戳"，用 `onupdate=datetime.utcnow` 参数

### 踩坑 5：Ergast 结果接口端点错误

**现象**：
调用 `fetch_ergast_race_result(year, round)` 返回空数据或 404。

**根因**：
Ergast API 的结果接口端点应该是 `{year}/{round}/results.json`，但代码写成了 `{year}/{round}.json`：

```python
# ❌ 错误端点
def fetch_ergast_race_result(year: int, round_num: int):
    return _fetch_ergast_data(
        endpoint=f"{year}/{round_num}.json",  # ← 这是赛程信息，不是结果！
        cache_key=cache_key,
        table_name="RaceTable"
    )

# ✅ 正确端点
def fetch_ergast_race_result(year: int, round_num: int):
    return _fetch_ergast_data(
        endpoint=f"{year}/{round_num}/results.json",  # ← 加 /results
        cache_key=f"result_{year}_{round_num}",
        table_name="RaceTable"
    )
```

**Ergast 端点对照**：

| 端点 | 返回内容 |
|------|---------|
| `{year}/{round}.json` | 该站赛程信息（赛道、时间等），无结果 |
| `{year}/{round}/results.json` | 该站比赛结果（名次、车手、车队等） |
| `{year}/{round}/qualifying.json` | 该站排位赛结果 |

**排查过程**：
1. 返回数据里没有 `Results` 字段，只有 `Races[0].Circuit`
2. 对比 Ergast 官方文档，发现端点少了 `/results`
3. 修改后返回正确的结果数据

**教训**：
- API 端点的每个路径段都有语义，少一段就完全不同
- 第三方 API 要先在浏览器/Postman 里手动测通，再写代码
- 返回数据结构和预期不符时，第一时间检查端点 URL
