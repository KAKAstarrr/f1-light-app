### 1.2 模块职责边界

| 模块 | 职责 | 技术边界 | 业务边界 |
|------|------|---------|---------|
| **路由层** (`main.py`) | 路由注册、参数校验、响应封装 | 不包含业务逻辑，只做参数转发 | 对外 API 契约 |
| **数据源层** (`data_source.py`) | 数据获取、三级缓存管理、类型转换 | 只返回 JSON 可序列化原生类型（timedelta/numpy 先转换） | 不处理业务规则 |
| **GameService** (`game_service.py`) | Fantasy 积分计算、芯片校验、转会逻辑 | 纯 Python 计算，不涉及 IO | 积分规则唯一真相源 |
| **PredictionService** (`prediction_service.py`) | 特征构建、模型加载、概率推理 | 模型 offline 训练，online 推理 | 预测结果供参考 |
| **鉴权层** (`auth.py`) | JWT 签发/校验、密码 bcrypt 哈希 | 只依赖 config 密钥与 ORM | 用户身份唯一真相源 |
| **数据库层** (`database.py`) | 连接管理、建表、**自动迁移补列** | `_auto_migrate()` 对比 ORM 与物理表，自动 ALTER TABLE | 不关心业务语义 |
| **缓存层** | 数据持久化、过期策略、空间管理 | 文件系统 IO，JSON/ff1pkl 格式 | 不关心数据语义 |
| **Streamlit 原型** (`streamlit_app.py`) | 纯 Python 数据看板 MVP | 独立入口，不参与主路由 | 验证数据 pipeline |

### 1.3 技术边界声明

- **不涉及**: 实时流处理（F1 数据本身为赛后批量获取）
- **不涉及**: 深度学习（XGBoost 已满足需求，深度模型在 20 维特征上容易过拟合）
- **不涉及**: WebSocket 实时推送（初版用轮询，进阶可选加）
- **数据粒度**: 圈速数据精确到毫秒，遥测数据精确到 0.1s 采样点
- **前端语言**: JavaScript（未引入 TypeScript，降低新手门槛；后续可渐进迁移）

### 2.3 实时 vs 离线责任划分

| 管线 | 触发方式 | 延迟要求 | 负责模块 | 现状 |
|------|---------|---------|---------|------|
| 赛程/成绩查询 | 用户请求 | < 2s | 数据源层 → 缓存 | ✅ 缓存命中 ~200ms |
| 遥测数据加载（首次） | 用户请求 | 60-120s（需下载 50-100MB） | FastF1 → .ff1pkl 缓存 | ✅ 前端 timeout=120s |
| 遥测数据加载（缓存命中） | 用户请求 | < 1s | fastf1_result_cache | ✅ |
| Fantasy 积分结算 | 定时任务 (赛后) | 赛后 1h 内 | GameService → Cron | 📋 Cron 待部署 |
| AI 预测推理 | 用户请求 + 赛前预计算 | < 1s | PredictionService | ✅ 规则模型 |
| 模型训练 | 手动/定时 (赛季前) | 离线 | ml/notebooks | 📋 XGBoost 待训练 |
| 动态定价更新 | 定时任务 (每站后) | 赛后 1h 内 | GameService → Cron | 📋 |
| 缓存清理 | 定时任务 (每日) | 低 | scripts/refresh_cache.sh | 📋 |

> ⚠️ **遥测延迟修正（v1.1）**：v1.0 声称「遥测加载 < 5s」不准确。FastF1 首次加载某分站需从 F1 官方下载 50-100MB `.ff1pkl` 原始数据，实测可能 60s+。因此前端遥测接口超时统一设为 **120s**，二次请求走缓存 < 1s。这是本项目最核心的性能瓶颈与缓存价值所在。

## 三、缓存策略详解

### 3.1 三级缓存架构

```
Level 1: Ergast JSON 缓存
  路径: cache/ergast_cache/*.json
  过期: 3600s（1 小时）← v1.1 修正（原为「永久」）
  策略: 首次查询写缓存，1 小时后过期自动刷新（赛季进行中数据会更新）
  代码: data_source.py 中 CACHE_EXPIRE_SECONDS = 3600

Level 2: FastF1 原始缓存
  路径: cache/fastf1_cache/*.ff1pkl
  过期: 永久（官方 .ff1pkl 格式，赛后数据不变）
  策略: FastF1 库内置缓存，自动管理
  手动刷新: 删除 cache/fastf1_cache/ 目录

Level 3: FastF1 结果缓存
  路径: cache/fastf1_result_cache/*.json
  过期: 7 天
  策略: 处理后的结构化 JSON，过期重新计算
  手动刷新: 删除对应缓存文件
```

### 3.2 缓存键设计

```python
# Ergast 缓存键
ergast_key = f"{endpoint}_{params_hash}.json"
# 例: "current_season.json", "race_result_2026_2.json", "driver_standings_2026.json"

# FastF1 结果缓存键
fastf1_key = f"{data_type}_{year}_{round}_{session_type}.json"
# 例: "fastlap_2026_2_R.json", "tyre_2025_1_R.json"

# 遥测缓存键（v1.1 提示）
# ⚠️ 多车手对比时须先排序再拼接：'-'.join(sorted(driver_codes))
# 否则 "VER,NOR" 与 "NOR,VER" 会生成两个重复缓存（体检报告 #14）
```

### 3.3 50-100MB 遥测数据处理策略

| 阶段 | 数据量 | 处理方式 |
|------|--------|---------|
| FastF1 加载 | 50-100MB（含 car_data/pos_data） | `session.load(laps=True, telemetry=True)`，缓存为 .ff1pkl |
| 数据提取 | ~20MB（仅需要的通道） | `laps.pick_fastest()` + 指定通道 `car_data[['Speed','Throttle','Brake','RPM','nGear','DRS']]` |
| API 返回 | < 1MB | 采样降频（每 10m 一个点）+ JSON 压缩 |
| 前端渲染 | < 500KB | ECharts 大数据模式，只渲染视口内数据点 |

**超时与异常兜底（v1.1 补充）：**
- 后端遥测接口统一 `try/except` 兜底，异常返回 `{code: 500, msg: ...}`，不抛裸异常
- 前端 `telemetry.js` 超时统一 120s（首次下载）；`request.js` 拦截器对遥测超时给出专属提示「数据量较大，第二次走缓存会快很多」
- 接口支持 `session_type` 参数（默认 "R"），Q1/Q2/Q3 统一映射到 FastF1 的 'Q' 会话
- 2026 赛季未举办分站返回「分站暂未开始」，不 fallback 到 mock

### 3.4 缓存空间管理

```
磁盘占用估算（完整 1 个赛季 ~24 站）:
  cache/ergast_cache/        ~5 MB    (JSON, 文本可压缩)
  cache/fastf1_cache/        ~3 GB    (24站 × 100MB/站)
  cache/fastf1_result_cache/ ~50 MB   (处理后的精简 JSON)
  cache/f1_app.db             <1 MB   (用户/Fantasy/投票 SQLite)

总计: ~3 GB
建议: 生产环境使用 SSD，本地开发可只缓存最近 3 站
      cache/ 已整体加入 .gitignore，不提交 GitHub
```

### 4.1 前端选型分析：为什么选 Vue 3 而不是 React

| 维度 | React 18 | Vue 3 | 结论 |
|------|----------|-------|------|
| **上手难度** | JSX 心智负担、Hooks 闭包陷阱、useEffect 依赖数组 | 模板语法直觉、响应式自动追踪、SFC 单文件组件 | Vue 胜 |
| **中文文档** | 翻译质量参差，核心概念英文优先 | 尤雨溪亲自维护，中文文档与英文同步 | Vue 胜 |
| **状态管理** | Redux/Zustand/Jotai 选择困难 | Pinia 官方唯一推荐，开箱即用 | Vue 胜 |
| **UI 组件库** | Ant Design(英文优先)、MUI(英文) | Element Plus(中文优先)、Naive UI(中文作者) | Vue 胜 |
| **TypeScript** | 完美支持 | 3.3+ 完美支持 | 持平 |
| **可视化生态** | echarts-for-react, react-leaflet | vue-echarts, vue3-leaflet | 持平 |
| **招聘市场** | 国际/大厂占优 | 国内中小企业占比高，增长快 | 看目标 |
| **学习曲线** | 2-3 周入门 | 3-5 天入门 | Vue 胜 |

> **决策**: 对于应届生/自学者的第一个全栈项目，Vue 3 的学习成本远低于 React。Vue 的模板语法接近于写 HTML，Composition API (`ref`/`reactive`/`watch`/`computed`) 的心智模型比 React Hooks 更直观。本项目实际落地：前端 2A.1-2A.9 全部用 Vue 3 完成并联调跑通。未来转 React 也只需 1-2 周适应期。

### 4.2 快速原型方案：Streamlit（✅ 已完成）

| 优势 | 劣势 |

## 七、简历话术提炼

### 7.1 架构设计能力
> "设计七层架构（前端展示→API→路由→服务→数据→缓存→存储），实现数据展示、遥测分析、Fantasy 玩法、AI 预测四大模块解耦，模块间通过 RESTful API + Pydantic 类型约束通信。前后端 40+ 页面/组件全栈联调落地。"

### 7.2 缓存设计能力
> "针对 FastF1 单次会话 50-100MB 遥测数据，设计三级缓存策略：Ergast 1 小时 JSON 缓存、FastF1 官方 .ff1pkl 原始缓存、处理后 7 天结果缓存。首次加载 60-120s → 缓存命中后 200ms，命中率 90%+。"

### 7.3 数据工程能力
> "构建离线/在线双管线：离线管线负责历史数据清洗+特征工程+模型训练（ml/notebooks），在线管线负责实时 API 响应+模型推理，通过 SQLite 自动迁移机制（`_auto_migrate`）解决模型演进导致的表结构变更，避免线上 500。"

### 7.4 前端工程能力
> "使用 Vue 3 Composition API + Pinia + ECharts 实现 GP Tempo 级遥测可视化：3 图联动（速度/油门刹车/Delta）、多车手动态显隐、DRS/挡位/RPM 6 通道叠加、距离归一化速度对比，全链路从 FastF1 原始数据到浏览器渲染。"

### 7.5 面试亮点
> **"你的架构是怎么设计的？"** → 拿出分层架构图，讲清楚每一层的职责边界和数据流向，强调三级缓存解决了 100MB 遥测数据的性能瓶颈，自动迁移机制解决了 SQLite 表结构演进的坑（登录 500 的真实排障案例）。
