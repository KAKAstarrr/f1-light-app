## 1. 三级缓存架构设计

### 概念
针对两种数据源的不同特性，设计三级缓存：

| 级别 | 缓存对象 | 路径 | 过期策略 | 理由 |
|------|---------|------|---------|------|
| L1 | Ergast API 响应 | `cache/ergast_cache/*.json` | 永久 | 历史赛果不变，永久缓存 |
| L2 | FastF1 原始计时数据 | `cache/fastf1_cache/*.ff1pkl` | 永久 | 官方格式，FastF1 库自管理 |
| L3 | FastF1 处理后结果 | `cache/fastf1_result_cache/*.json` | 7 天 | 处理逻辑可能优化，留刷新窗口 |

```
请求 → L3 结果缓存命中? → 是 → 直接返回 JSON（~50ms）
                         → 否 → L2 .ff1pkl 缓存命中?
                                   → 是 → session.load() 读本地 → pandas 处理 → 写 L3 → 返回
                                   → 否 → 联网下载 → 写 L2 → 处理 → 写 L3 → 返回
```

### 本项目代码（data_source.py）
```python
# L1: Ergast 永久缓存
CACHE_EXPIRE_SECONDS = 999999999  # 几十年 ≈ 永久

def _fetch_ergast_data(endpoint, cache_key, table_name):
    cache_data = load_from_cache(cache_key)     # 查 L1
    if cache_data is not None:
        return cache_data
    raw = requests.get(url).json()
    result = raw["MRData"][table_name]
    save_to_cache(cache_key, result)            # 写 L1
    return result

# L2: FastF1 原始缓存（库自管理）
fastf1.Cache.enable_cache(FASTF1_HTTP_CACHE)

# L3: 结果缓存（7天过期）

def fetch_fastf1_fastest_lap(year, round_num, session_type):
    cached = _load_fastf1_result(cache_key)     # 查 L3
    if cached is not None:
        return cached
    laps_df = fetch_fastf1_sessions(...)        # 读 L2

```

### 面试问答
**Q: 为什么不用 Redis 而用文件缓存？**
> 项目初期用户量为 0，文件缓存零依赖、零成本、够用。Redis 需要额外部署和运维。当并发上来后（DAU > 100）再迁移 Redis，代码层只需改 `load_from_cache` / `save_to_cache` 两个函数。

**Q: 缓存穿透、缓存雪崩、缓存击穿是什么？你的项目怎么处理？**
> - **穿透**：查询不存在的数据，缓存和数据库都没有，每次都穿透到后端。本项目返回 `{code:500,msg}` 并缓存该结果，下次同样请求命中缓存直接返回。
> - **雪崩**：大量缓存同时过期，瞬间流量打到后端。本项目的 Ergast 缓存永不过期，FastF1 结果缓存 7 天过期但请求量低，不会雪崩。
> - **击穿**：热点 key 过期瞬间大量请求打到后端。本项目单用户场景不存在，生产环境可用互斥锁（第一个请求加锁查 DB 并回填缓存，其他请求等待）。

**Q: 永久缓存有什么风险？**
> 数据源修正了历史数据后，本地缓存不会自动更新。需要手动刷新机制（本项目提供 `scripts/refresh_cache.sh`）。Ergast 赛程数据一旦产生就不变，永久缓存合理；如果是股票价格等变动数据，绝不能永久缓存。

## 2. API 分层架构

### 概念
将后端分为路由层和数据源层，职责分离：

```
main.py（路由层）          data_source.py（数据源层）
┌──────────────┐          ┌──────────────────────┐
│ 路由注册      │  调用    │ Ergast 请求 + 缓存    │
│ 参数校验      │ ──────→ │ FastF1 加载 + 缓存    │
│ CORS 配置     │          │ pandas 数据处理       │
│ 响应返回      │ ←────── │ 类型转换（原生类型）   │
└──────────────┘  返回    └──────────────────────┘
```

**核心原则**：路由层不碰数据细节，数据源层不碰 HTTP 细节。

### 本项目代码

**路由层（main.py）—— 纯转发**
```python
@app.get("/api/fastf1/{year}/{round}/fast-lap")
def get_fastf1_fastest_lap(year: int, round: int, session_type: str = 'R'):
    return fetch_fastf1_fastest_lap(year, round, session_type)
    # ↑ 只接收参数、调用函数、返回结果，3 行搞定
```

**数据源层（data_source.py）—— 封装所有复杂逻辑**
```python
def fetch_fastf1_fastest_lap(year, round_num, session_type):
    # 1. 查结果缓存
    # 2. 加载 session
    # 3. pandas 清洗
    # 4. groupby 取最快
    # 5. 类型转换
    # 6. 写缓存
    # 7. 返回
```

### 面试问答
**Q: 为什么要分层？不分层会怎样？**
> 不分层 = 所有逻辑写在 main.py 里，路由函数又长又乱，改一个缓存逻辑要改所有路由。分层后：换数据源（如 Ergast → 另一个 API）只改 data_source.py，路由层零修改；加缓存只改 data_source.py；加新接口 main.py 加 3 行 + data_source.py 加一个函数。

**Q: data_source.py 为什么只返回原生类型？**
> FastAPI 默认用 `json.dumps()` 序列化返回值，它不认识 `timedelta64[ns]` / `numpy.int64`。如果数据源层返回这些类型，路由层需要逐个转换，违反分层原则。在数据源层统一转成 `int/float/str/None/list/dict`，路由层直接返回即可。

## 3. timedelta / numpy 序列化

### 概念
FastF1 的 `LapTime` 是 `timedelta64[ns]`（pandas 时间差类型），`to_dict("records")` 返回 `numpy.int64/float64`。这些类型无法被标准 `json.dumps()` 序列化。

```python
# ❌ 会报错
import json
json.dumps({"time": pd.Timedelta(seconds=82.167)})
# TypeError: Object of type Timedelta is not JSON serializable

# ✅ 先转原生类型
json.dumps({"time": 82.167})  # 正常
```

### 本项目代码（data_source.py —— 两个工具函数）
```python
def _timedelta_to_seconds(td):
    """timedelta / NaT → float 秒数，NaT 返回 None"""
    if td is None or pd.isna(td):
        return None
    try:
        return float(td.total_seconds())
    except AttributeError:
        return float(td)   # 已经是数字

def _format_laptime(td):
    """timedelta → 'M:SS.mmm' 格式，如 1:22.167"""
    sec = _timedelta_to_seconds(td)
    if sec is None:
        return None
    minutes = int(sec // 60)
    remainder = sec - minutes * 60
    return f"{minutes}:{remainder:06.3f}"
```

**类型转换链**：
```python
# to_dict("records") 出来的是 numpy 类型，需手动转
for item in data_list:
    item["Rank"] = int(item["Rank"])                    # numpy.int64 → int
    item["LapTimeSeconds"] = round(float(item["LapTimeSeconds"]), 3)  # numpy.float64 → float
```

### 面试问答
**Q: 为什么不用自定义 JSONEncoder？**
> 自定义 Encoder 需要在 FastAPI 的 `response_class` 里配置，且每个类型都要写 `default()` 分支。在数据源层直接转原生类型更简单、更显式，调试时也能直接看到返回值是原生类型。Encoder 方案适合无法控制返回值的场景（如第三方库直接返回）。

**Q: `pd.isna()` 和 `pd.isnull()` 区别？**
> 完全等价，`pd.isnull` 是 `pd.isna` 的别名。都返回 bool：NaN/NaT/None → True。注意 `np.isnan()` 只处理 float NaN，遇到 None 会报错。

## 4. FastF1 最快圈提取

### 概念
从 laps 表中提取每位车手的最快一圈，按时间升序排列。

```
原始 laps 表（~1000 行，每圈一行）
    ↓ dropna(LapTime)           去掉无效圈
    ↓ apply(timedelta→seconds)  时间转秒
    ↓ groupby(Driver).idxmin()  每人最快圈的行索引
    ↓ sort_values(ascending)    按时间升序
    ↓ reset_index + Rank        加排名
    → 最快圈排行
```

### 本项目代码（data_source.py）
```python
def fetch_fastf1_fastest_lap(year, round_num, session_type="R"):
    # ... 缓存检查 ...

    laps_df = fetch_fastf1_sessions(year, round_num, session_type)
    df = laps_df.dropna(subset=["LapTime"]).copy()           # 去掉无效圈
    df["LapTimeSeconds"] = df["LapTime"].apply(_timedelta_to_seconds)
    df = df.dropna(subset=["LapTimeSeconds"])

    # 每位车手取最快一圈
    idx = df.groupby("Driver")["LapTimeSeconds"].idxmin()    # 关键：idxmin 返回最小值的行索引
    fastest = df.loc[idx, ["Driver", "LapTime", "LapTimeSeconds"]].copy()
    fastest = fastest.sort_values("LapTimeSeconds", ascending=True).reset_index(drop=True)
    fastest["LapTimeStr"] = fastest["LapTime"].apply(_format_laptime)
    fastest["Rank"] = (fastest.index + 1).astype(int)

    data_list = fastest[["Rank", "Driver", "LapTimeStr", "LapTimeSeconds"]].to_dict("records")
    for item in data_list:
        item["Rank"] = int(item["Rank"])
        item["LapTimeSeconds"] = round(float(item["LapTimeSeconds"]), 3)

    return {
        "code": 200,
        "fastest_lap_overall": data_list[0] if data_list else None,
        "fastest_lap_ranking": data_list,
    }
```

### 面试问答
**Q: `groupby().idxmin()` 和 `groupby().min()` 区别？**
> `min()` 只返回最小值本身（标量），丢失了其他列。`idxmin()` 返回最小值所在行的索引，可以用 `.loc[idx]` 取出完整行（包括 Driver、LapTime、Compound 等）。需要整行数据时用 `idxmin()`。

**Q: 为什么排序用 `ascending=True`？**
> 圈速越短越快（1:22 比 1:25 快），所以升序排列（短的在前）= 快的在前。如果按积分排序则降序（多的在前）。

**Q: `dropna(subset=["LapTime"])` 为什么要先做？**
> 进站圈、出场圈的 LapTime 可能是 NaT（Not a Time）。如果不 dropna，`groupby().idxmin()` 会因为 NaT 无法比较而报错或返回错误结果。

## 5. 轮胎策略按 Stint 重建

### 概念
轮胎策略 = 每位车手在比赛中换了哪些轮胎、每段跑了多少圈。

```
错误做法：groupby(['Driver','Compound']).count()
    → NOR: {SOFT: 15, MEDIUM: 20}    ← 丢失顺序！不知道先软后硬还是先硬后软

正确做法：groupby(['Driver','Stint'])
    → NOR: [
        {stint:1, compound:SOFT,   laps:15, start:1,  end:15},
        {stint:2, compound:MEDIUM, laps:20, start:16, end:35}
    ]                                  ← 保留进站顺序
```

### 本项目代码（data_source.py）
```python
def fetch_fastf1_tyre_strategy(year, round_num):
    # ... 缓存检查 ...

    laps_df = fetch_fastf1_sessions(year, round_num, session_type="R")
    df = laps_df[["Driver", "Stint", "Compound", "LapNumber"]].copy()
    df = df.sort_values(["Driver", "LapNumber"])

    strategy = []
    for driver, grp in df.groupby("Driver", sort=False):
        stints = []
        for stint_no, sg in grp.groupby("Stint", sort=False):   # 关键：按 Stint 分组
            compound = sg["Compound"].iloc[0]
            if compound is None or (isinstance(compound, float) and np.isnan(compound)):
                compound = "UNKNOWN"                              # 兜底：NaN → UNKNOWN
            stints.append({
                "stint": int(stint_no),
                "compound": str(compound),
                "start_lap": int(sg["LapNumber"].min()),
                "end_lap": int(sg["LapNumber"].max()),
                "laps": int(len(sg)),
            })
        if stints:
            strategy.append({"driver": str(driver), "stints": stints})

    return {"code": 200, "tyre_strategy": strategy}
```

### 面试问答
**Q: `groupby(sort=False)` 为什么加 `sort=False`？**
> 默认 `groupby` 会按分组键排序（Driver 字母序、Stint 数字序），但我们需要保留数据原始顺序（赛道上的实际出场顺序）。`sort=False` 保持原始顺序，性能也更好（省排序）。

**Q: `compound` 为什么可能是 NaN？**
> 极少见但确实会发生：进站换胎的瞬间，系统可能记录了一行没有 Compound 的数据（换胎过程中传感器未读到）。用 `isinstance(compound, float) and np.isnan(compound)` 检测并兜底为 "UNKNOWN"。

**Q: 前端怎么用这个数据画轮胎策略条带图？**
> 每个车手一行，按 stint 顺序画色块：SOFT=红、MEDIUM=黄、HARD=白、INTERMEDIATE=绿、WET=蓝。色块宽度 = laps 数量。这是 F1 直播中经典的轮胎策略可视化。

## 6. 异常兜底与优雅降级

### 概念
第三方数据源不稳定（网络超时、数据缺失、格式变化），必须在整个链路中兜底，保证一个接口出错不影响其他接口。

```
请求 → session.load() 失败?  → 返回 {code:500, msg:"暂无数据"}  ← 优雅降级
       ↓ 成功
       pandas 处理出错?       → 返回 {code:500, msg:"处理失败"}
       ↓ 成功
       返回正常数据 {code:200, ...}
```

### 本项目代码（data_source.py —— 三层兜底）
```python
# 第一层：session.load() 异常
def fetch_fastf1_sessions(year, round_num, session_type="R"):
    try:
        session = fastf1.get_session(year, round_num, session_type)
        session.load(laps=True, telemetry=False, weather=False, messages=False)
    except Exception as e:
        print(f"[FastF1 加载失败] {year} 第{round_num}站：{e}")
        return None                          # ← 不抛异常，返回 None

    laps = getattr(session, "laps", None)
    if laps is None or len(laps) == 0:
        return None                          # ← 空数据也返回 None
    return laps

# 第二层：业务函数检查 None
def fetch_fastf1_fastest_lap(year, round_num, session_type="R"):
    laps_df = fetch_fastf1_sessions(year, round_num, session_type)
    if laps_df is None:
        return {"code": 500, "msg": f"暂无 {year} 第{round_num}站 {session_type} 圈速数据"}

    df = laps_df.dropna(subset=["LapTime"]).copy()
    if df.empty:
        return {"code": 500, "msg": "本场无有效圈速（LapTime 全为空）"}  # ← 第三层兜底

    # ... 正常处理 ...

# Ergast 层：网络超时兜底
def _fetch_ergast_data(endpoint, cache_key, table_name):
    try:
        resp = requests.get(url, timeout=6)
        resp.raise_for_status()
    except requests.exceptions.RequestException:
        raise HTTPException(status_code=504, detail="Ergast接口访问超时")
```

### 面试问答
**Q: 为什么用 `return None` 而不是 `raise Exception`？**
> 数据缺失不是异常，是正常业务情况（如 2026 年第 99 站不存在）。用 `None` 表示"没有数据"，让上层决定怎么处理（返回 500 JSON 或用缓存兜底）。如果 `raise Exception`，FastAPI 会返回 500 + 堆栈信息，前端无法优雅展示。

**Q: `getattr(session, "laps", None)` 为什么用 getattr？**
> 防御性编程。`session.load()` 可能因为数据不完整而没有创建 `laps` 属性。直接 `session.laps` 会抛 `AttributeError`，用 `getattr` 带 default 更安全。

**Q: `timeout=6` 为什么设 6 秒？**
> Ergast API 正常响应 < 1 秒。6 秒是容忍网络抖动的上限：太短（如 2 秒）会误杀慢请求，太长（如 30 秒）会让用户等太久。没有完美值，根据经验调。

## 7. 缓存键设计与过期策略

### 概念
缓存键是唯一标识缓存数据的字符串，设计原则：**唯一性 + 可追溯性**。

```python
# Ergast 缓存键
"current_season"                    # 当前赛季
"season_2025"                       # 2025 赛季
"result_2025_1"                     # 2025 第 1 站结果
"qualifying_standings_2025_1"       # 2025 第 1 站排位

# FastF1 结果缓存键
"fastlap_2025_1_R"                  # 2025 第 1 站正赛最快圈
"tyre_2025_1_R"                     # 2025 第 1 站正赛轮胎策略
```

### 过期检查逻辑
```python
def _is_cache_valid(file_path):
    if not os.path.exists(file_path):
        return False
    modify_time = os.path.getmtime(file_path)    # 文件最后修改时间
    now = time.time()
    return now - modify_time < CACHE_EXPIRE_SECONDS   # 是否在有效期内

def _is_fastf1_result_cache_valid(file_path):
    if not os.path.exists(file_path):
        return False
    return (time.time() - os.path.getmtime(file_path)) < 7 * 24 * 3600  # 7 天
```

### 本项目缓存键设计
```python
# Ergast：永久缓存，键名直接对应业务含义
cache_key = f"result_{year}_{round_num}"

# FastF1：7 天过期，键名含 session_type 区分正赛/排位
cache_key = f"fastlap_{year}_{round_num}_{session_type}"
```

### 面试问答
**Q: 缓存键为什么要包含所有参数？**
> 缓存键是唯一标识。`fastlap_2025_1_R` 和 `fastlap_2025_1_Q` 是不同的数据（正赛最快圈 vs 排位赛最快圈），键里必须包含 `session_type`。如果只写 `fastlap_2025_1`，排位赛请求会命中正赛缓存返回错误数据。

**Q: 文件缓存的过期检查有什么缺陷？**
> 基于 `mtime`（文件修改时间）：如果手动 touch 文件（不改内容），mtime 会更新，缓存"永不过期"。另外，系统时间回拨（NTP 校时）会导致过期判断异常。生产环境用 Redis 的 TTL 更可靠。

**Q: 缓存写失败怎么处理？**
> 本项目用 `try/except OSError: pass`——缓存写失败不影响主流程，只是下次请求会重新计算。这是正确的做法：缓存是优化手段，不是核心逻辑，不能因为缓存写失败就让请求失败。

## 8. 项目踩坑实录

### 踩坑 1：`session.load()` 参数名错误
**现象**：`TypeError: Session.load() got an unexpected keyword argument 'message'`
**根因**：参数是 `messages`（复数），部分教程/旧版写 `message`。
**修复**：`session.load(laps=True, telemetry=False, weather=False, messages=False)`
**教训**：第三方库 API 以源码为准，inspect.signature() 验证。

### 踩坑 2：轮胎列名 `TyreCompound` 不存在
**现象**：`KeyError: 'TyreCompound'`
**根因**：FastF1 3.x 的列名是 `Compound`，旧教程写 `TyreCompound`。
**修复**：`laps_df["Compound"]`
**教训**：先 `print(laps.columns)` 看实际列名，不要信教程。

### 踩坑 3：`LapTime` 序列化失败
**现象**：FastAPI 返回 500，日志 `TypeError: Object of type Timedelta is not JSON serializable`
**根因**：`LapTime` 是 `timedelta64[ns]`，标准 json 不支持。
**修复**：`_timedelta_to_seconds()` + `_format_laptime()` 统一转换。
**教训**：数据源层必须返回原生类型，非标准类型在出口统一转换。

### 踩坑 4：`groupby().count()` 丢失进站顺序
**现象**：轮胎策略只显示每种配方跑了多少圈，不知道先后顺序。
**根因**：`groupby(['Driver','Compound']).count()` 把同配方圈数合并，丢失了 Stint 信息。
**修复**：按 `Stint` 分组，保留每段轮胎的 start_lap/end_lap。
**教训**：聚合前想清楚业务需要什么信息，别为了简单丢掉关键维度。

### 踩坑 5：异常分站导致服务崩溃
**现象**：请求不存在的分站（round=99），FastF1 抛 `Invalid round`，服务 500 崩溃。
**根因**：没有 try/except 兜底。
**修复**：`fetch_fastf1_sessions` 全包 try/except，返回 None；上层检查 None 返回 `{code:500,msg}`。
**教训**：第三方数据源的不稳定性必须在架构层面兜底。

### 踩坑 6：`to_dict("records")` 返回 numpy 类型
**现象**：`json.dumps()` 在某些路径报 `TypeError: Object of type int64 is not JSON serializable`
**根因**：pandas `to_dict()` 返回的值是 `numpy.int64/float64`，不是 Python 原生 `int/float`。
**修复**：遍历 data_list，用 `int()` / `float()` 显式转换。
**教训**：pandas 数据出口必须做类型清洗，不能直接丢给序列化器。
