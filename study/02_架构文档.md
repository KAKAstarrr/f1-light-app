### 1.2 模块职责边界

| 模块 | 职责 | 技术边界 | 业务边界 |
|------|------|---------|---------|
| **路由层** (`main.py`) | 路由注册、参数校验、响应封装 | 不包含业务逻辑，只做参数转发 | 对外 API 契约 |
| **数据源层** (`data_source.py`) | 数据获取、缓存管理、类型转换 | 只返回 JSON 可序列化原生类型 | 不处理业务规则 |
| **GameService** | Fantasy 积分计算、芯片校验、转会逻辑 | 纯 Python 计算，不涉及 IO | 积分规则唯一真相源 |
| **PredictionService** | 特征构建、模型加载、概率推理 | 模型 offline 训练，online 推理 | 预测结果供参考 |
| **缓存层** | 数据持久化、过期策略、空间管理 | 文件系统 IO，JSON/ff1pkl 格式 | 不关心数据语义 |

### 1.3 技术边界声明

- **不涉及**: 实时流处理（F1 数据本身为赛后批量获取）
- **不涉及**: 深度学习（XGBoost 已满足需求，深度模型在 20 维特征上容易过拟合）
- **不涉及**: WebSocket 实时推送（初版用轮询，进阶可选加）
- **数据粒度**: 圈速数据精确到毫秒，遥测数据精确到 0.1s 采样点

### 2.3 实时 vs 离线责任划分

| 管线 | 触发方式 | 延迟要求 | 负责模块 |
|------|---------|---------|---------|
| 赛程/成绩查询 | 用户请求 | < 2s | 数据源层 → 缓存 |
| 遥测数据加载 | 用户请求 | < 5s | FastF1 → 缓存 |
| Fantasy 积分结算 | 定时任务 (赛后) | 赛后 1h 内 | GameService → Cron |
| AI 预测推理 | 用户请求 + 赛前预计算 | < 1s | PredictionService |
| 模型训练 | 手动/定时 (赛季前) | 离线 | Jupyter Notebook |
| 动态定价更新 | 定时任务 (每站后) | 赛后 1h 内 | GameService → Cron |
| 缓存清理 | 定时任务 (每日) | 低 | Shell 脚本 |

## 三、缓存策略详解

### 3.1 三级缓存架构

```
Level 1: Ergast JSON 缓存
  路径: cache/ergast_cache/*.json
  过期: 永久（赛程数据不变）
  策略: 首次查询写缓存，后续永不过期
  手动刷新: API /admin/refresh-ergast

Level 2: FastF1 原始缓存
  路径: cache/fastf1_cache/*.ff1pkl + SQLite
  过期: 永久（官方 .ff1pkl 格式）
  策略: FastF1 库内置缓存，自动管理
  手动刷新: 删除 cache/fastf1_cache/ 目录

Level 3: FastF1 结果缓存
  路径: cache/fastf1_result_cache/*.json
  过期: 7 天
  策略: 处理后的结构化 JSON，过期重新计算
  手动刷新: API /admin/refresh-fastf1
```

### 3.2 缓存键设计

```python
# Ergast 缓存键
ergast_key = f"{endpoint}_{params_hash}.json"
# 例: "current_season.json", "race_result_2026_2.json"

# FastF1 结果缓存键
fastf1_key = f"{data_type}_{year}_{round}_{session_type}.json"
# 例: "fastlap_2026_2_R.json", "tyre_2025_1_R.json"
```

### 3.3 50-100MB 遥测数据处理策略

| 阶段 | 数据量 | 处理方式 |
|------|--------|---------|
| FastF1 加载 | 50-100MB（含 car_data/pos_data） | `session.load(laps=True, telemetry=True)`，缓存为 .ff1pkl |
| 数据提取 | ~20MB（仅需要的通道） | `laps.pick_fastest()` + 指定通道 `car_data[['Speed','Throttle','Brake','RPM','nGear','DRS']]` |
| API 返回 | < 1MB | 采样降频（每 10m 一个点）+ JSON 压缩 |
| 前端渲染 | < 500KB | 只渲染视口内数据点，Canvas 虚拟滚动 |

### 3.4 缓存空间管理

```
磁盘占用估算（完整 1 个赛季 ~24 站）:
  cache/ergast_cache/        ~5 MB    (JSON, 文本可压缩)
  cache/fastf1_cache/        ~3 GB    (24站 × 100MB/站 + SQLite 索引)
  cache/fastf1_result_cache/ ~50 MB   (处理后的精简 JSON)

总计: ~3 GB
建议: 生产环境使用 SSD，本地开发可只缓存最近 3 站
```

### 4.1 前端选型分析：为什么选 Vue 3 而不是 React

| 维度 | React 18 | Vue 3 | 结论 |
|------|----------|-------|------|
| **上手难度** | JSX 心智负担、Hooks 闭包陷阱、useEffect 依赖数组 | 模板语法直觉、响应式自动追踪、SFC 单文件组件 | Vue 胜 |
| **中文文档** | 翻译质量参差，核心概念英文优先 | 尤雨溪亲自维护，中文文档与英文同步 | Vue 胜 |
| **状态管理** | Redux/Zustand/Jotai 选择困难 | Pinia 官方唯一推荐，开箱即用 | Vue 胜 |
| **UI 组件库** | Ant Design(英文优先)、MUI(英文) | Element Plus(中文优先)、Naive UI(中文作者) | Vue 胜 |
| **TypeScript** | 完美支持 | 3.3+ 完美支持 | 持平 |
| **可视化生态** | echarts-for-react, react-leaflet | vue-echarts, vue3-leaflet | 持平 |
| **招聘市场** | 国际/大厂占优 | 国内中小企业占比高，增长快 | 看目标 |
| **学习曲线** | 2-3 周入门 | 3-5 天入门 | Vue 胜 |

> **决策**: 对于应届生/自学者的第一个全栈项目，Vue 3 的学习成本远低于 React。Vue 的模板语法接近于写 HTML，Composition API (`ref`/`reactive`/`watch`/`computed`) 的心智模型比 React Hooks 更直观。先拿 Vue 3 做出成品，未来转 React 也只需 1-2 周适应期。

### 4.2 快速原型方案：Streamlit（可选）

在正式开发 Vue 3 前端之前，可以用 **Streamlit** 先做出数据展示原型：

```python
# 纯 Python，零前端代码
import streamlit as st
st.title("F1 2026 赛季赛程")
data = requests.get("http://localhost:8000/api/current-season").json()
st.dataframe(data)
```

| 优势 | 劣势 |
|------|------|
| 纯 Python，后端开发者零学习成本 | 无法自定义 UI/交互 |
| 30 分钟就能做一个数据看板 | 不支持复杂路由/SPA |
| 内置 chart/table/map 组件 | 简历价值低于 Vue/React |
| 适合快速验证数据 pipeline | 不适合作为最终产品 |

> **建议路径**: Streamlit 做数据看板 MVP（1 天）→ Vue 3 正式前端（4 周）。两阶段产出都能放进简历。

## 七、简历话术提炼

### 7.1 架构设计能力
> "设计分层架构（路由层→服务层→数据层→缓存层），实现数据展示、互动玩法、AI 预测三大模块解耦，模块间通过 RESTful API + 类型约束通信。"

### 7.2 缓存设计能力
> "针对 FastF1 单次会话 50-100MB 遥测数据，设计三级缓存策略：Ergast 永久 JSON 缓存、FastF1 官方 .ff1pkl 原始缓存、处理后 7 天结果缓存，API 响应从 30s 降至 200ms（缓存命中率 90%+）。"

### 7.3 数据工程能力
> "构建离线/在线双管线：离线管线负责赛季前历史数据清洗+特征工程+模型训练，在线管线负责实时 API 响应+模型推理，通过 Cron 定时任务实现 Fantasy 积分自动结算。"

### 7.4 面试亮点
> **"你的架构是怎么设计的？"** → 拿出分层架构图，讲清楚每一层的职责边界和数据流向，强调缓存策略解决了 100MB 遥测数据的性能瓶颈。
