## 一、产品概述

### 1.1 一句话定位
**用真实 F1 数据 + AI 模型打造的「观赛 + 分析 + 预测 + 互动」一体化全栈应用。**

### 1.2 核心差异化
| 维度 | 竞品/同类项目 | 本产品 |
|------|-------------|--------|
| 数据深度 | 大多数展示静态成绩 | 接入 FastF1 遥测数据，对标 GP Tempo 可视化 |
| AI 能力 | 几乎没有 ML 落地 | XGBoost 多分类夺冠概率预测，特征工程可解释 |
| 互动玩法 | 纯展示型 | 自研 Fantasy + 投票 + 联盟排行榜 |
| 简历价值 | "做了个博客" | 全栈 + 数据工程 + ML + 产品设计 |

### 1.3 对标产品分析

**GP Tempo (gp-tempo.com) 核心能力拆解：**
| 能力 | GP Tempo 实现 | 本产品对标方案 |
|------|-------------|--------------|
| 赛道地图最快分段着色 | Leaflet 地图 + 分段着色 | 复用 FastF1 `get_circuit_info()` 坐标，前端 Canvas/SVG 渲染 |
| 车手/会话/年份遥测对比 | 多选车手叠加折线图 | Chart.js/ECharts 多系列叠加，支持 session_type 切换 |
| 最快圈自动选取 | 自动选 Purple Sector | `session.laps.pick_fastest()` + 分段计算 |
| Tooltip 精确读数 | 鼠标悬停读数 | Chart.js tooltip 回调 + 自定义精度格式 |
| 圈速分布 | 小提琴/箱线图 | `laps.groupby('Driver')['LapTime']` + Plotly/ECharts |
| 速度叠加 | 多通道速度曲线 | 速度/油门/刹车/RPM/挡位/DRS 六通道可选 |
| 遥测通道 | Speed/Throttle/Brake/RPM/nGear/DRS | 完全对标，加 Weather 数据融合 |

## 二、用户画像

### 2.1 四类核心用户

| 画像 | 描述 | 核心诉求 | 使用频率 |
|------|------|---------|---------|
| **F1 轻度观众** | 每周看比赛，关注结果和积分 | 赛程、成绩速览、车手排名 | 赛前/赛后 |
| **F1 硬核车迷** | 研究遥测数据、轮胎策略 | 遥测对比、圈速分析、赛道分段 | 赛中/赛后 |
| **Fantasy 玩家** | 喜欢竞猜、排名比拼 | Fantasy 组队、联盟 PK、实时积分 | 赛前排名 |
| **AI/技术学习者** | 关注 ML 落地、技术实现 | 预测模型、特征工程、开源代码 | 随时 |

### 2.2 用户场景故事

- **周五排位赛后**: 小白用户打开 App 看排位结果 → 查看 AI 预测的正赛夺冠概率 → 根据预测调整 Fantasy 阵容
- **周日正赛直播中**: 硬核车迷对比两位车手的 S1/S2/S3 分段圈速 + 遥测数据 → 分享到联盟讨论区
- **周一赛后**: 运营查看投票结果 → 发布最佳车手 → Fantasy 自动结算积分 → 更新联盟排行榜
- **开发阶段**: AI 学习者 clone 项目 → 运行 Jupyter Notebook 复现特征工程 → 调试 XGBoost 参数 → 贡献 PR

**关键实现踩坑（已在模块 A 完成时验证）：**
- `session.load()` 参数名是 `messages` 不是 `message`
- 轮胎列名是 `Compound` 不是 `TyreCompound`
- `LapTime` 是 `timedelta64[ns]`，须转秒/格式化
- 轮胎策略须按 `Stint` 分组保持进站顺序，不可只 groupby compound 计数
- 部分分站需 `try/except` 兜底
- 遥测接口首次加载需下载 50-100MB 原始数据，前端超时须设 120s（v1.1 补充）

### 3.3 模块 C：Fantasy 小游戏（新增）

#### 3.3.1 自研积分规则（简化版）

| 事件 | 积分 | 说明 |
|------|------|------|
| 车手完赛（Top 10 内） | +10 / 8 / 6 / 5 / 4 / 3 / 2 / 1 / 0 / 0 | 按名次递减 |
| 车手排位赛 Top 3 | +3 / +2 / +1 | 排位赛奖励 |
| 车手 DNF（退赛） | -5 | 惩罚退赛 |
| 车队完赛（Top 5 内） | +5 / 4 / 3 / 2 / 1 | 按车队最好名次 |
| 全场最快圈 | +5 | 车手额外加分 |
| 位置提升（vs 排位） | +1×提升位次 | 发车后每提升 1 位 |
| x2 Boost（队长） | 车手积分 ×2 | 选 1 名车手为队长 |

**与官方 F1 Fantasy 的差异：**
| 项目 | 官方 | 本产品 |
|------|------|--------|
| 预算 | $100M | ¥100M（符号替换） |
| 阵容 | 5 车手 + 2 车队 | 5 车手 + 2 车队（一致） |
| 转会 | 免费 2 次/站 | 免费 2 次/站 |
| 芯片 | Limitless/Wildcard/No Negative 等 | 简化版 3 种芯片（见下） |
| 定价 | 动态官方定价 | 基于赛季积分 + 近期表现的动态定价算法 |

#### 3.3.2 简化芯片系统

| 芯片 | 效果 | 使用次数/赛季 |
|------|------|-------------|
| **Limitless** | 本站无视预算限制，任意选人 | 2 次 |
| **Wildcard** | 本站无限制转会，可不消耗免费转会次数 | 2 次 |
| **No Negative** | 本站 DNF/退赛不扣分 | 1 次 |

#### 3.3.3 动态定价算法
```
driver_price = base_price × (0.5 + 0.5 × season_points_ratio)
  + trend_bonus（近 3 场得分趋势）
  - penalty（DNF 惩罚，每次 -2M，最多 -10M）

其中 base_price 根据上赛季排名分配：
  Top 3: 30M, Top 5: 25M, Top 10: 20M, 其余: 15M, 新秀: 10M
```

### 3.4 模块 D：AI 夺冠概率预测（✅ 页面已实现，模型待升级 ⭐ 简历核心）

#### 3.4.1 目标
赛前输出每位车手的夺冠概率分布（多分类），Top 3 预测。

> **v1.1 状态**：Prediction.vue 页面已实现并锁定 upcoming 站；当前使用规则加权模型（`prediction_service.py`），XGBoost 多分类为规划升级方向（📋）。

#### 3.4.2 特征工程维度

| 维度 | 特征 | 数据源 | 说明 |
|------|------|--------|------|
| **车手状态** | 近 5 场平均完赛位次 | Ergast | 最近状态 |
| | 历史胜率 | Ergast | 生涯冠军占比 |
| | 排位赛平均位次 | Ergast | 发车位置关联 |
| | 该赛道历史最佳 | Ergast | 赛道适应性 |
| | 近期 DNF 次数 | Ergast | 可靠性 |
| **车队趋势** | 赛季积分趋势（近 3 场） | Ergast | 上升/下降 |
| | 车队历史该赛道最佳 | Ergast | 车队赛道特性 |
| | 队友对比差距 | Ergast | 车队内部实力差 |
| **赛道特性** | 赛道类型（街道/永久/混合） | 静态标注 | 分类编码 |
| | 超车难度指数 | 静态数据 | 历史超车数 |
| | 历史杆位转化率 | Ergast | 发车→冠军概率 |
| | 弯道数 / DRS 区数 | 静态数据 | 赛道复杂度 |
| **环境** | 天气预报（干/湿） | FastF1/外部 API | 轮胎策略影响 |
| | 气温 | FastF1 weather | 轮胎工作窗口 |
| **综合** | 前一场结果（carry-over） | Ergast | momentum 效应 |

#### 3.4.3 模型方案

```
模型: XGBoost 多分类 (multi:softprob)
标签: 完赛名次（可简化为 Top1 / Top3 / Top5 / Top10 / 其他 五分类）
训练: 2018-2025 赛季数据，5 折时间序列交叉验证
评估: Top3 命中率 / LogLoss / Confusion Matrix / 特征重要性 SHAP
部署: joblib/pickle 保存模型，FastAPI 加载推理
```

## 七、简历话术提炼

### 7.1 项目描述（一行版）
> 基于 FastF1 遥测数据与 Ergast 历史数据库，构建集「GP Tempo 级数据可视化 + 自研 Fantasy 积分玩法 + XGBoost 夺冠概率预测」于一体的 F1 全栈分析平台。

### 7.2 核心亮点（三点版）
1. **数据工程**: 设计三级缓存架构（Ergast 永久 / FastF1 原始 / 结果 7 天），处理单次 50-100MB 遥测数据，API P95 < 3s
2. **机器学习**: 构建 20+ 维特征工程体系，XGBoost 多分类预测夺冠 Top3，SHAP 解释模型决策
3. **产品设计**: 自研 Fantasy 积分规则 + 动态定价算法 + 芯片系统，对标官方 F1 Fantasy 机制

### 7.3 面试问答准备

| 面试问题 | 回答要点 |
|---------|---------|
| "为什么选 XGBoost？" | 表格数据表现稳定，特征重要性可解释（SHAP），工业界验证充分，比深度学习更适合中小数据集 |
| "如何处理 100MB 的单次遥测数据？" | 三级缓存策略：FastF1 官方 .ff1pkl → 处理后 JSON → 前端只返回必要字段，减少传输 |
| "Fantasy 积分规则如何设计？" | 参考官方 + 简化，核心是"偏差惩罚"机制，动态定价基于赛季积分 + 近 3 场趋势 |
| "项目最大的技术难点？" | FastF1 数据不稳定性（不同分站字段差异），用 try/except 兜底 + 类型统一转换 + 缓存降级 |
