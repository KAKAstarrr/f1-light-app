## 二、模块 A 技术复盘

### 2.1 架构决策回顾

| 决策 | 选择 | 理由 | 反思 |
|------|------|------|------|
| Ergast 数据源 | jolpica-f1 镜像 | 原 ergast.com 已停用 | ✅ 正确，jolpica 响应更快 |
| 数据源分层 | data_source.py 独立模块 | 单一职责，路由层不碰缓存 | ✅ 设计合理，后续模块 B 遥测可复用缓存层 |
| 所有返回类型 | 统一为 JSON 可序列化原生类型 | 避免 timedelta/numpy 序列化失败 | ✅ 关键设计决策，省去大量调试时间 |
| 轮胎策略存储 | 按 Stint 分组保留顺序 | 不可只 groupby compound | ✅ 进站顺序对策略分析至关重要 |
| 异常处理 | try/except 返回 500 | 不因一场数据损坏崩溃整个服务 | ✅ 稳健做法 |

### 2.2 核心踩坑记录

| 编号 | 坑 | 根因 | 解决方案 |
|------|-----|------|---------|
| #1 | `session.load()` 报错 | 参数名是 `messages` 不是 `message` | FastF1 文档 vs 源码不一致 |
| #2 | 轮胎列找不到 | 列名是 `Compound` 不是 `TyreCompound` | 查看 `laps.columns` 确认 |
| #3 | JSON 序列化报错 | `LapTime` 是 `timedelta64[ns]` | `_timedelta_to_seconds()` + `_format_laptime()` |
| #4 | 轮胎策略数据错误 | groupby compound 丢失顺序 | 改为按 `Stint` 分组 |
| #5 | 异常分站崩溃 | 某些分站数据不完整 | try/except 兜底 + 返回 {code:500, msg} |
| #6 | Ergast API 不可用 | 原域名停用 | 切换到 api.jolpi.ca 镜像 |

**经验教训**: 
- FastF1 API 文档与源码有差异，遇到参数问题先看源码
- 第三方数据源的不稳定性需要在架构层面兜底（缓存 + try/except + 降级）
- 类型转换是 Python 数据管线的噩梦，需要在数据源层统一处理

### 2.3 缓存效果评估

| 场景 | 无缓存 | 一级缓存 (Ergast) | 二级缓存 (FastF1) | 三级缓存 (Result) |
|------|--------|-------------------|--------------------|--------------------|
| 获取赛程 | ~500ms | ~5ms | - | - |
| 获取比赛结果 | ~600ms | ~5ms | - | - |
| 获取最快圈 | ~30s | - | ~15s | ~50ms |
| 获取轮胎策略 | ~15s | - | ~8s | ~30ms |

**缓存命中率预期**: Ergast 99%+，FastF1 结果缓存 90%+（7 天过期）

## 二-B、模块 B 技术复盘（遥测分析：B1/B2/B3）

### B.1 架构决策回顾

| 决策 | 选择 | 理由 | 反思 |
|------|------|------|------|
| 分段最快数据源 | FastF1 laps 表 `Sector1Time`/`Sector2Time`/`Sector3Time` | 直接使用官方分段计时，无需手动切分 | ✅ 数据准确，Ergast 无分段数据 |
| 圈速分布可视化 | ECharts boxplot + 异常值散点 | 箱线图是圈速分布的标准统计图 | ✅ 五数概括 + IQR 异常值规则，符合统计学规范 |
| 遥测降采样策略 | `step = max(1, len(car_data) // 200)` | 原始 20Hz 数据 ~20MB，前端无法承受 | ✅ 降到 200 点后图表渲染流畅，趋势保留完整 |
| 通道映射 | `speed→Speed`、`gear→nGear` | FastF1 car_data 列名与常见直觉不同 | ⚠️ nGear 的 `n` 前缀容易遗漏 |
| TeleCompare 动态化 | 年份/分站选择器 + Pinia store | 原硬编码 `year: 2023, round: 1` 无法切换比赛 | ✅ 用户可自由选择 2023-2025 任意分站 |

### B.2 核心踩坑记录（模块 B）

| 编号 | 坑 | 根因 | 解决方案 |
|------|-----|------|---------|
| #B1 | Sector 列名找不到 | 列名是 `Sector1Time` 不是 `Sector1` | 查看 `laps.columns` 确认完整列名 |
| #B2 | 分段时间 NaT 报错 | 进站圈/首圈 Sector 时间可能为 NaT | `dropna()` 过滤无效分段 |
| #B3 | nGear 列名错误 | 习惯写 `Gear`，实际是 `nGear` | 通道映射表加注释提醒 `n` 前缀 |
| #B4 | ECharts boxplot 不显示 | data 格式不是 `[min, Q1, median, Q3, max]` | 手动排序后取位置计算五数概括 |
| #B5 | ECharts 内存泄漏 | 组件卸载未 `dispose()` | `onUnmounted` 中销毁所有实例 |
| #B6 | TeleCompare 硬编码年份 | 原 `year: 2023, round: 1` 写死 | 重写为选择器 + Pinia store 加载赛程 |
| #B7 | 端口 8000 僵尸套接字 | Windows 进程被杀但端口残留 | 换端口 8001 测试 / 重启系统 |
| #B8 | __pycache__ 导致路由不生效 | 旧 .pyc 文件被加载 | `rm -rf backend/__pycache__` 后重启 |

### B.4 经验教训

1. **ECharts 生命周期管理是前端必考题**：`echarts.init()` → `setOption()` → `dispose()`，漏掉 `dispose()` 在频繁切换页面时内存持续增长
2. **降采样算法的精度取舍**：200 点足以展示遥测趋势（速度曲线/油门变化），但无法体现瞬时峰值（如刹车点尖峰），后续可考虑保留峰值点的智能降采样
3. **FastF1 列名的不一致性**：`Sector1Time` vs `Sector1`、`nGear` vs `Gear`、`Compound` vs `TyreCompound` —— 每次新增数据维度都要先 `print(laps.columns)` 或 `print(car_data.columns)` 确认
4. **箱线图前端实现比后端复杂**：后端只返回原始圈速数组，Q1/Q3/异常值全部在前端 JS 中计算，这要求前端开发者理解统计学概念

### C.4 体检经验教训

1. **SQLite `create_all` 不等于迁移工具**：它只建新表、不补旧表新列。给 ORM 模型加字段后老库必炸 → 轻量自动迁移函数是必配
2. **路由重定向是递归高危区**：`path: ''` + redirect 到自己 → 栈溢出。规则：**重定向目标路径不能再匹配当前路由**，或改用组件内默认值
3. **体检要先验证再下结论**：Ergast 的 `position`/`grid`/`FastestLap.rank` 都是**字符串**（用真实缓存数据实证），`"1"` 字符串匹配最快圈是正确的；F1 状态码还有 `Engine`/`Disqualified` 等非 Retired 退赛
4. **前端废弃 API 是长期噪音源**：Vue Router `next()`、Element Plus `:label` 这类警告现在不修，升级版本就变硬错误——体检时应顺手清零

## 三、模块 3 技术复盘（数据库 + AI + Fantasy + 投票）

### 3.1 架构决策回顾

| 决策 | 选择 | 理由 | 反思 |
|------|------|------|------|
| ORM 框架 | SQLAlchemy 2.0 | Python 生态标准，自动建表 | ✅ 开发效率高，切 PostgreSQL 仅改连接串 |
| 密码哈希 | bcrypt 直接调用 | passlib 与 bcrypt 5.0 不兼容 | ✅ 去掉中间层，减少依赖冲突 |
| JWT 库 | python-jose | 轻量，不依赖大型框架 | ✅ 够用，token 签发/校验 20 行代码 |
| AI 模型 | 规则加权（非 XGBoost） | 先跑通端到端流程，特征维度与 XGBoost 一致 | ✅ 快速验证，后续替换仅需改 predict_race() |
| 数据库 | SQLite | 零配置，开发阶段够用 | ✅ 正确选择，生产切 PostgreSQL 一行代码 |
| Fantasy 定价 | 简化版（基于积分排名） | 完整动态定价需要历史数据积累 | ✅ 先跑通，后续接入 calculate_driver_price() |

## 九、Windows 端口残留 + Vite proxy 500 故障复盘（2026-08-14）

### 9.1 故障现象

F1 前端"AI 预测"页面加载时浏览器 console：

```
GET http://localhost:8010/api/current-season 500 (Internal Server Error)
  at async Proxy.fetchRaceList (race.js:10)
  at async fetchRaceList (filterBar.vue:1293)
  ...
```

实际涉及前端 4 个组件，都因同一个接口 500 失败：
- `filterBar.vue`（顶栏赛历下拉）
- `RaceNav.vue`（赛历导航）
- `RaceCenter.vue`（赛历中心）
- `Prediction.vue`（AI 预测）

### 9.2 排查过程

1. `curl http://127.0.0.1:8010/api/current-season` → **HTTP=500**
2. `ls cache/ergast_cache/current_season.json` → 文件存在且 JSON 完整（24 站 2026 赛季）
3. `code backend/data_source.py::fetch_ergast_current_season` → 逻辑简单到几乎不可能出错
4. `netstat -ano | grep :8010` → **发现端口上有 3 个僵尸 LISTEN socket**（PID 12564/35432/34472）
5. 对比：新启动到 8012 的 uvicorn 立即返回 **HTTP=200**，确认不是代码 bug

### 9.3 根因

```
uvicorn --reload (主进程) 
    ├── worker 1 (PID 35432)  ← 监听 8010
    ├── worker 2 (PID 12564)  ← 监听 8010 (SO_REUSEADDR)
    └── worker 3 (PID 34472)  ← 监听 8010 (SO_REUSEADDR)
```

Windows + uvicorn `--reload` 在代码改动后会产生 fork/terminate 风暴：

- **进程死了**，但 TCP socket **没释放**（Windows 网络栈 bug，常见于 `TerminateProcess`）
- 新 worker 起来时**仍能 bind**（SO_REUSEADDR），于是一个端口有 3 个独立 LISTEN
- 内核**随机分发**新进来的连接 — 落到的可能是 stale worker，它持有的：
  - 内存里的 SQLAlchemy session 已断开
  - 加载的 XGBoost 模型状态错乱
  - 任何 `try/except` 之外的非预期路径 → 直接抛 500

Vite proxy `/api → http://localhost:8010`：浏览器 → proxy → **随机一个僵尸 worker** → 500。

### 9.4 修复

| 步骤 | 命令 | 说明 |
|------|------|------|
| 1 | `netstat -ano \| grep :8010` | 列出 LISTEN 占用 PID |
| 2 | `taskkill /F /PID <pid>` 或 PowerShell `Stop-Process -Id <pid> -Force` | 强杀 worker |
| 3 | `Start-Sleep 5~15` | 等内核释放 socket（Windows TIME_WAIT/LISTEN 残留最长 15s） |
| 4 | `python -m uvicorn backend.main:app --port 8010 --log-level info` | 启动健康实例 |

### 9.5 防御脚本：`scripts/restart_backend.py`

为避免再次踩坑，一次性写好自愈脚本：

```bash
python scripts/restart_backend.py             # 默认 8010
python scripts/restart_backend.py --port 8011 # 其它端口
python scripts/restart_backend.py --no-start  # 只清端口，不启动
```

**核心逻辑**（基于 `psutil`）：

1. **遍历所有进程**：跳自己 PID（避免自杀），找出：
   - 端口 LISTEN 占用者
   - 路径含 `f1_project` 的 python
2. **`proc.kill()`** 干净杀掉
3. **轮询等 socket 释放**（最多 15s），失败时 `netsh int ip reset`
4. **`subprocess.Popen` + `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`** 标志位启动 uvicorn，
   让它**完全独立于父进程**（`Start-Process` 在 PowerShell 5.1 上有 PATH 解析 bug，不可用）

为什么不用 `.bat` / PowerShell：

- `.bat` 的 `start /B "" "exe" args > log 2>&1` 在 PowerShell 嵌套调用下出现 unicode 截断（uvicorn 被吃成 `'vicorn' 不是内部或外部命令`）
- `Start-Process -FilePath ...` 在 PowerShell 5.1 + 含 `f1_project` 路径的进程时触发 `字典关键字 Path 重复` bug
- 用 Python + `subprocess.Popen` + `DETACHED_PROCESS` 标志位最稳

配套另有 **`scripts/start_backend.bat`**（无自动清理能力，仅作为日常快速启动使用）。

### 9.6 教训

1. **Windows + uvicorn reload 是一对不稳定的搭配** — 长期方案是放弃 `--reload`，改用文件 watcher（`watchdog`/`nodemon`）外部触发重启
2. **任何 500 都先看端口层**：`netstat -ano | grep :PORT` > 1 个 LISTEN → 立刻想到僵尸 socket
3. **后端 500 + 前端 CORS 报错同框出现，先看后端日志**，别查 CORS 配置 — FastAPI 500 不带 CORS 头，浏览器会自动报成 CORS 问题（误判）
4. **自愈脚本要常驻 scripts/**：所有"未来可能再次发生的相同现象"都该有对应一键脚本，而不是每次手忙脚乱

### 9.7 简历话术补强

> - **工程化细节**：解决 Windows + uvicorn reload 模式下 socket 残留导致 Vite proxy 转发 500 的稳定性问题，编写 `psutil` + `DETACHED_PROCESS` 标志位的自愈脚本，显著降低重启排查时间。
